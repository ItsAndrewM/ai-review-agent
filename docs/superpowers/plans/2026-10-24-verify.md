# Verify Pass Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a second model pass that keeps or drops each blocking finding and suggestion, sets its severity, and drives the review's event from the verified findings. It is measured offline against Andrew's bar before it is switched on.

**Architecture:** the pure parts live in `src/review/verify.ts`:
- picking the candidates;
- applying the verdicts;
- the approve rule;
- the prompt and the answer parser;
- retry and the backstop;
- the standing check after verify.

The display changes live in `render.ts` and `check.ts`. Settings resolve in `config.ts` into `pending`. The object runs verify inside `postReview`, between the final `checkSubmission` and `publishReview`, as its own Pi session whose operation id the review owns, through a `submit_verdicts` tool. A replay harness under `tools/verify-replay/` scores verdicts on the audit's labelled set.

**Tech Stack:** TypeScript on Cloudflare Workers with a Durable Object, Pi Durable through `agents/harness/pi`, TypeBox, vitest, and Workers AI (GLM-5.3 Flash, Kimi K2.7 Code).

**Spec:** `docs/superpowers/specs/2026-10-24-verify-design.md`. Read it first: the decisions there bind this plan, and its Q numbers are cited below.

## Global Constraints

- **Lint** (`CLAUDE.md`):
  - no comments of any kind, no JSDoc and no dodge-the-rule `SAFETY:` comments;
  - no type assertions except `as const`;
  - complexity at most 10;
  - anti-slop: no `unknown` or `object` parameters or returns (only a caught error's `cause`), no `typeof` checks, no `...(cond ? {...} : {})` spreads, no "shape" in names, no `vi.mock`.
- **Parsing:** everything that crosses a boundary is parsed with a TypeBox schema and `Value.Check`: model tool arguments, a JSON-as-text answer, a job or stored record.
- **TypeScript:** `exactOptionalPropertyTypes` and `noUncheckedIndexedAccess` are on.
- **Every task:** `pnpm format`, then `pnpm check` passes (lint, typecheck and every test).
- **`VERIFY_MODEL` stays `""` (off) in `wrangler.jsonc`** until Task 9 sets the measured default. Merging this work must not turn verify on.
- **Free models first:** the default verify model follows Q4's rule. If only Kimi clears the bar, stop and show Andrew its measured cost per review and per day before setting it.
- **Production is shared:** agree a deploy window with the other andabot sessions before any deploy, and restore plain main after it.
- **Never use bare `git stash`.** Commit or push only as these tasks say.
- **Before the PR,** merge `origin/main` into the branch. Main has moved past `a08b6ca`, with #108 and #109 and more since.

## Review Focus

The inputs the spec implies but no task's main tests exercise, most likely first. Each gets a test in the task named.

1. **Two verdicts for one finding id:** the first applies, and later ones are ignored and counted as unknown (Task 2).
2. **A cited file that can't be read** (deleted, on the base for `LEFT`, or a fetch error): the finding still goes to verify with "file unavailable" in place of its window, and verify can still call `read_file` (Task 3).
3. **A verify answer written as text,** whether fenced JSON, bare JSON or prose. JSON with valid verdicts is used, and anything else is an unusable answer, which fails the attempt (Task 3, Task 4).
4. **Findings bunched in one file:** windows that overlap show the file's lines once per finding, which is accepted, and up to `MAX_FINDINGS` (25) candidates build one prompt (Task 3).
5. **The head moving, or `pending` being replaced, while verify runs:** nothing is posted (Task 4's `standingAfterVerify`).

### Task 2: Candidates, verdicts and the approve rule (pure)

**Files:**
- Create: `src/review/verify.ts`
- Test: `test/verify.test.ts`

**Interfaces:**
- **Consumes:** `FindingInput`, `Rejected`, `ValidatedReview` and `holdsApprovalBack` from `findings.ts` and `render.ts`; `ScopedReview` and `applyDeltaPolicy` from `incremental.ts`.
- **Produces:**
  - `VerdictInput`, a TypeBox schema: `{ finding: string /* "F1" */, keep: boolean, severity: Severity, reason: string (minLength 1) }`;
  - `VerdictsSubmission = Type.Object({ verdicts: Type.Array(VerdictInput) })`;
  - `interface VerifyCandidate { id: string; finding: FindingInput; held: boolean }`;
  - `verifyCandidates(scoped: ScopedReview): VerifyCandidate[]`;
  - `interface VerifyReport { dropped: Judged[]; changed: Changed[]; capped: Judged[]; notJudged: FindingInput[]; unknown: string[] }`, with `Judged = { finding: FindingInput; reason: string }` and `Changed = Judged & { from: Severity; to: Severity }`;
  - `applyVerdicts(validated: ValidatedReview, candidates: readonly VerifyCandidate[], verdicts: readonly VerdictInput[]): { validated: ValidatedReview; report: VerifyReport }`;
  - `verdictAfterVerify(verdict: ReviewSubmissionInput["verdict"], before: ScopedReview, after: ScopedReview): ReviewSubmissionInput["verdict"]`.

- [ ] **Step 1: Write the failing tests** in `test/verify.test.ts`, with fixtures built by a local `finding({...})` helper, as in `test/approval.test.ts`:
  - **Candidates:** `verifyCandidates` takes accepted blocking findings and suggestions in order as `F1..Fn`, skips nitpicks, and adds rejected findings where `holdsApprovalBack` is true with `held: true`. Rejected non-blocking or unfounded findings are skipped.
  - **Keep:** a keep at the same severity leaves the finding as it was and reports nothing.
  - **Drop:** an accepted finding is removed and reported in `dropped` with its reason. A held finding is removed from `rejected`.
  - **Promote:** a suggestion with basis `defect` and verdict `blocking` is reported in `changed` with `{ from: "suggestion", to: "blocking" }`.
  - **Capped:** a suggestion with basis `standard` or `test` and verdict `blocking` keeps `suggestion` and is reported in `capped`.
  - **Demote:** a blocking finding demoted to `suggestion` is reported in `changed`. A held finding demoted to `suggestion` stays in `rejected` with the new severity, and `holdsApprovalBack` is now false for it.
  - **Missing verdict:** a candidate without a verdict lands in `notJudged`, unchanged.
  - **Unknown ids:** a verdict for `"F9"` with 2 candidates goes in `unknown: ["F9"]`.
  - **Duplicates (Review Focus 1):** with two verdicts for `F1`, the first applies and `unknown` gets `"F1"`.
  - **Delta interplay:**
    - In an `incremental` scope, a blocking finding on a line outside `covered`, demoted to `suggestion`, ends up in `applyDeltaPolicy(applied.validated, scope).rejected`.
    - A blocking finding on a non-blocking open thread's line, demoted, ends up in `duplicates`.
  - **The approve rule:** `verdictAfterVerify`:
    - gives `"approve"` for `"request_changes"` when `before` had a blocking finding (accepted or held) and `after` has none;
    - gives `"request_changes"` when one remains;
    - gives `"request_changes"` when `before` had none, since verify removed nothing;
    - leaves `"comment"` as `"comment"` in every case.
- [ ] **Step 2: Run** `pnpm exec vitest run test/verify.test.ts` and expect it to FAIL, since the module is missing.
- [ ] **Step 3: Implement** `src/review/verify.ts`:
  - Severity changes replace the finding object with `{ ...finding, severity }`.
  - The basis cap uses the same rule `validateFindings` applies: `standard` and `test` can't be blocking.
  - The function is pure, with no I/O.
- [ ] **Step 4: Run** `pnpm check` and expect it to PASS.
- [ ] **Step 5: Commit:** "Pick verify's candidates, apply its verdicts with the basis cap and the delta rules, and approve a request for changes verify cleared".
