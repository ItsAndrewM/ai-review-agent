# andabot: design

`andabot` is a self-hosted pull request reviewer in the shape of CodeRabbit: it reviews every PR on its own, answers when tagged, posts a summary and inline findings with suggestions, requests changes when it finds something, and approves once its findings are resolved. It runs on Cloudflare: a Worker receives GitHub webhooks and hands each PR to its own Durable Object, where Pi Durable runs the agent loop.

Status: phase 1, the walking skeleton, is built, deployed and reviewing this repository's pull requests (#1), and `pnpm check` runs on every pull request in GitHub Actions (#3). Phase 2's skills work has shipped its three slices, each measured on #2: the review procedure as skills (#11), basis, coverage and the spec axis (#22), and repository context (#29, #28, #75). Slice 3's catalog ruling stands: a repository's own skills reach the model through the Agents SDK catalog, which GLM-5.3 Flash called cleanly on #54 on 22 Oct 2026, while the built-in skill and its references stay inline. The verify pass (#31) is built and ships off, with `VERIFY_MODEL` empty: its 24 Oct replay found that neither GLM nor Kimi met the activation bar. Phase 3, the sandbox tier, is shipped and on by default since #135's measurement of 29 Oct 2026: on the fixtures #142, #143 and #144, GLM-5.3 Flash confirmed a planted test failure and a planted type error with `run_check`, cited the runs, and never asked for the sandbox on the docs-only change, for $0.002 to $0.003 of container time a review, and Kimi K2.7 Code did the same with every check it could run, for $0.005; what a hostile pull request can cost is bounded under "Execution tiers".

## Decisions so far

| Question | Decision | Why |
| --- | --- | --- |
| Agent harness | Pi Durable through the Agents SDK's `PiHarness` | Every turn, tool call and piece of state is committed before it is shown; idempotent submissions by request id; hooks before and after tool calls; survives eviction. Smallest loop of the three options. |
| Approval policy | Request changes on actionable findings, approve when they are resolved | CodeRabbit's request-changes workflow, which is the feature worth keeping. |
| Plan | Workers Paid, since 17 Oct 2026 | Unlocks Workers AI's paid models, such as Kimi K2.7 Code, and Containers for the sandbox tier. Reviews run on GLM-5.3 Flash since #2 compared models on 19 Oct 2026. |
| Repos | Andrew's own repos, public and private, through one GitHub App named `andabot` | An App's approval counts toward required reviews like a person's. The default Actions token's does not without an org setting. |
| State | One Durable Object per pull request | Memory per PR for chat follow-ups, the approval state machine and incremental review live where the PR does. |

Both `PiHarness` and Pi Durable are beta. APIs will move, so every package is pinned and upgrades are deliberate.

## Architecture

```
GitHub ──webhook──▶ Worker (router)
                      │  verify X-Hub-Signature-256
                      │  forward X-GitHub-Delivery; Pi dedupes by request id
                      │  installation token cache
                      ▼
            PullRequest Durable Object  (one per installation/repo#number)
            ├─ SQLite: reviewed head, summary comment id, bot threads, config
            ├─ PiHarness ─ Pi Durable session (transcript, tasks, inbox)
            │     tools: pr, diff, read_file, tree, grep
            │     hooks: validate findings against diff hunks before posting
            ├─ Snapshot: the head's text files in SQLite, searched by grep and tree
            └─ ReviewSandbox (Containers, #131): a command on the head, egress through Outbound
                      │
                      ▼
            GitHub REST: reviews, review comments, issue comments, checks
```

### Router Worker

- Verifies the webhook HMAC with the App's webhook secret. Rejects anything else.
- Uses the delivery id (`X-GitHub-Delivery`) as the Pi submission's `requestId`, so a GitHub redelivery cannot post twice.
- Mints and caches the installation token: App JWT (RS256 over WebCrypto) → `POST /app/installations/{id}/access_tokens`, cached for ~55 minutes in the PR object or a small KV.
- Routes by event to `env.PR.getByName(`${installationId}/${owner}/${repo}#${number}`)`.

Events the App subscribes to:

| Event | Action | Handler |
| --- | --- | --- |
| `pull_request` | opened, synchronize, reopened, ready_for_review | review (incremental on synchronize), skipped while paused; a draft is forwarded too, and the object applies `reviews.drafts` from `.andabot.yaml`; on opened, a 👀 on a description that tags andabot, draft or not |
| `pull_request` | edited | ignored, so a title or base edit starts no review; the next push or a command does |
| `pull_request` | closed, merged included | drop the repository snapshot once no review or answer is running (#93); routed even when a bot sent it, since a merge queue or a bot can close a pull request |
| `issue_comment` | created, on a PR | a 👀, then a command or chat turn |
| `pull_request_review` | submitted | a summary that tags andabot: a 👀, then a command or chat turn answered in the conversation |
| `pull_request_review_comment` | created | a mention, or a reply in one of andabot's threads: a 👀, then the answer in that thread, with its file, line and hunk |
| `pull_request_review_thread` | resolved, unresolved | re-evaluate approval; ignored when a bot sent it, so andabot's own resolutions are left to the review or the `resolve` that made them; a draft's is forwarded, and the evaluation waits as `not_open` |
| `check_run` / `check_suite` | rerequested | full review of each listed pull request; dormant, since GitHub shows no Re-run on andabot's runs (#8) |
| `check_suite` | requested | ignored: the pull request event starts the review |
| `check_suite` | completed | re-evaluate approval for each listed pull request, skipping andabot's own suite; routed even when a bot sent it, since GitHub Actions' suites arrive from `github-actions[bot]` |
| `check_run` | completed | ignored: its suite's completion follows |

App permissions: Pull requests write, Contents read, Issues write, Checks write (the review check run), Metadata read.

### PullRequest Durable Object

State in its SQLite, beside Pi's `pi_` tables:

- `reviewed`: the head of the last review, the base branch's name, the mode it ran in, the summary and walkthrough of the last full review or of a later `summary`, and the merge danger the summary shows for the whole pull request, which an incremental review keeps, escalating it to one-way with the push's blast radius when the push is one-way (#124), with a `since` section from the latest incremental one that carries the push's own judgement, and how long the last review took in seconds (#50). A written walkthrough row for a file outside the reviewable set is dropped before the record is written, on a review and on a `summary` (#119). A `summary` replaces the summary, walkthrough and merge danger, deletes `since`, and keeps the rest, the head and the seconds included. The next push diffs against that head, and a different base branch (a retargeted pull request) means a full review.
- `summary_comment_id`, stored as `summaryCommentId`: the one issue comment that reviews, `summary`, `pause`, `resume` and the evaluation's approval edit in place.
- `finding:<commentId>`: the severity, title and quoted line of each inline comment the bot posted. Thread state isn't stored. Whether a thread is resolved or outdated, and where it sits now, is read live from GitHub on each review, so a thread a person resolved is always seen as resolved. These records only supply what GitHub doesn't: the quote to catch a repeat, and the severity that gates approval.
- `scope`: the plan of the review in flight. It holds the mode, the range, the marked lines of each covered file, every one of the bot's open threads with its handle, the threads to re-check, and the `path_filters` that left files out of the prompt. `submitReview` applies it to the submission, so a review is validated against what its prompt showed.
- `last_review`, stored as `lastReview`: the id, event (`REQUEST_CHANGES`, `COMMENT`, `APPROVE`) and head of the review the bot last submitted, the approval evaluation's own approvals included, with the count of reasons it withheld approval for (`withheld`, #122), the verdict the review's summary showed (`AWAITING_CHECKS` for a comment whose approval waits for the checks, `WITHHELD` for one that withheld it), the counts of its posted findings by severity, the count of blocking findings it couldn't post inline, and the request-changes workflow the review ran under. The evaluation's approval records the workflow as on, the only one it approves under, and carries the counts over. The approval evaluation reads it, and a `summary` rebuilds the comment's verdict line from it.
- `paused`: `true` while paused, written by `pause` and deleted by `resume` (#27); absent means not paused. The pause gate at the top of `review()` and the approval evaluation read it.
- `pausedBy`: the login that paused, for the summary comment's paused line. A key of its own leaves `paused` the plain `true` the evaluation reads.
- `pending`: the review in flight, with its head, delivery id, operation id, start time, the time it opened (`openedAt`, kept through retries and resumes, which the elapsed time counts from) and check run id, the model and skill fingerprint that attribute it, the request-changes workflow it runs under, the verify model it resolved (absent when verify is off), the error of an `.andabot.yaml` it ignored, the numbers of the linked issues its prompt carried, the paths of the instruction files its standards were rendered from, the fingerprint of the repository skills the catalog offered it, and whether its rejected findings, duplicates and missing walkthrough rows have gone back to the model; one per object, because reviews are single-flight.
- `summarizing`: the `summary` in flight, with its delivery id, operation id and start time; one per object, and live while Pi lists its operation or for two minutes after it starts or the model answers, the grace a pending review has.
- `summarySession`: the id of the Pi session summaries run in, created by the first `summary` and reset before each run.
- `verifySession`: the id of the Pi session verify runs in, created by the first verify run and reset before each attempt and when a review starts.
- `context:<baseSha>`: the repository at a pull request's base commit, as the review's standards and skills read it: the trees listing, kept to the blobs that may be instruction files and those under `.github/skills/`, `.agents/skills/` and `.claude/skills/`, each with its size and mode, and the instruction files and skill files loaded so far, a file missing at that commit as an empty body. A new base replaces it, and a record that fails its schema is deleted and fetched again, which is how its format changes: a record from before the sizes were kept is fetched again, while one from before the modes were kept still reads, its modes unknown.
- `config:<baseSha>`: the `.andabot.yaml` at a pull request's base commit as it was read: its settings with the defaults filled in, whether a file was there, and the error that made it ignored. A file GitHub failed to serve is never stored, so the next review reads it again. A new base replaces the record, and a record that fails its schema is deleted and read again.

Methods, each an idempotent Pi submission:

- `onPush(head, delivery)`: full review on first sight, incremental review (`compare reviewed...head`) after that.
- `onCommand(comment, delivery)`: `review`, `full review`, `summary`, `resolve`, `pause`, `resume`, `help`, else a chat turn.
- `evaluateApproval(trigger)`: after a thread is resolved or unresolved, after a check suite finishes, after a review that doesn't approve, after `resolve`, on `resume`, and on a re-check that a check suite's evaluation scheduled. It makes no model call, so it is no Pi submission.

Reviews are single-flight per pull request. A newer head aborts the running review, verify's operations included, and cancels its check run as superseded. A request for a head whose review is still running is skipped. A pending review the harness no longer lists, in the root session or in verify's, is dead: its run is failed and the new review proceeds. A record whose start time is under two minutes old counts as live. The grace bounds only the host's work while none of the review's operations is listed: before its first prompt is submitted, between that prompt and the retry, and after each. So the record is written before the first prompt, and its start time restarts when each prompt returns and again before the retry. The replacer deletes the record, aborts the replaced review's operations, and only then completes its run, from the id it read before the delete, so the replaced review's exits find the record gone and touch nothing. A review replaced before its prompt never prompts, and the run it opened is cancelled as superseded, or as replaced when the newer review is of the same head. A `submit_review` call posts only from the root conversation, while the root session's running operation is one the record names, and the host posts a review the model wrote as text only while the record still names its delivery. A record written before records kept a start time is outside any grace, so only the harness listing keeps it live. A review releases its record before it completes its own run, so a newer head that reads the record during that GitHub call finds it gone and can't mark a finished run superseded. A review that finds itself replaced logs `review.superseded` when the newer review is of another head, and `review.withdrawn` when it is of the same head. When the replacer has deleted the record but the newer review hasn't written its own yet, the review reads the pull request's head from GitHub to tell which; if that read fails, it logs `review.head_unreadable` and `review.withdrawn`. The `posted:<sha>` record keeps the review's finding counts and whether it was unverified, so a later run of that head that finds it posted completes with the same title, ` (unverified)` included.

The object is addressed only through the router. It has no public HTTP surface.

Every delivery enters the object through one door, `accept`, which keeps it in storage under `delivery:<id>:<kind>` (one delivery can carry a reaction and a review) until its handling completes, and replays it when the handling throws a transient GitHub error (#118): a `GitHubError` with a 5xx status, Cloudflare's 52x included, or no status at all because the fetch itself failed, or a `TransientFailure` the host raised, as the approval branch does for a transient evaluation that no re-check job will repeat. A 4xx, a mismatched response and a model failure are final and never retried here. The replay is a Lifecycle job, `event.retry`, keyed by delivery and kind, on a ladder of 30 s, 2 min and 10 min, so an outage of the length seen on 23 Oct 2026 is spanned and a healthy GitHub costs nothing; the job catches what the replay throws and schedules the next rung itself. A retried review resumes its own `pending` (`decideFlight` answers `resume` for the delivery that holds it, once the harness lists no running operation) under the check run that stayed in progress, since a transient throw in the review keeps the `pending` and the run where a final one completes the run as failed and releases it; so a head shows one check run with one outcome. The reads that used to soften a failure into an answer (`threadFor`, `latestHeadSha`, `compareSince`, `threadPlan`, `resolveScope`) rethrow a transient error so the delivery retries, and keep their soft answer for a final one; `reviewed` is never advanced by a failed read. When the ladder is spent the author is told where they look: a review's check run completes as failed, created at that point if none had opened, saying GitHub was unreachable and that `@andabot review` retries; a comment that could not be handled gets a reply saying the same; an approval or a close is logged only, since the next event re-checks or tears down. No catch-up on a later event: the next push reviews from the last reviewed head. The logs are `event.failed` (`delivery`, `kind`, `attempt`, `transient`, `error`, once per failed attempt), `event.retry` (the same plus `inMs`), `event.abandoned` (`delivery`, `kind`, `attempts`, `error`), `event.abandon_failed`, `event.retry_skipped` (`delivery`, `kind`, `attempt`, `reason`: `no_record`, when a redelivery or a completed attempt forgot the record before the rung fired), and `review.resumed` (`number`, `head`, `delivery`). The design is `docs/superpowers/specs/2026-10-29-reviews-that-hold-up-design.md`, slice 1.

After a deploy, Cloudflare moves the Worker and its Durable Objects to the new build eventually, so for seconds to minutes a new Worker can call an object still running the previous build, with that build's model and logic. The Worker passes its version with each event: `review.start` logs `staleBuild` and `callerBuild`, and `review.failed` logs `staleBuild`, so a failure during a rollout can be traced to it. The next event, or `@andabot review`, runs on the new build. When Pi resumes an interrupted review on the new build, the summary footer and the `posted:<sha>` record still take the model and skill fingerprint from `pending`, where `review()` stored those of the build that started it. The footer's linked issues come from `pending` too, where the run recorded the issues its prompt was built with. A linked issue that cannot be read (a 410 for a deleted issue, a 5xx) is skipped and logged as `review.issue_unreadable`, so optional context never fails a review.

### Pi harness inside the object

Following Cloudflare's `examples/next/harnesses/pi`: `createAI({ binding: env.AI })` as the Pi AI provider, `createRegistry()` with one extension for the system prompt and tools and another for verify's tools, which the settings' default selection leaves out (see Verify), joined per review by the skills catalog when the repository has skills (see Skills), `Harness.open(storage, { models, registry, settings })` in the `PiHarness` factory, `Lifecycle.install(this).use(this.harness)`.

Pi applies the harness's `defaults` only when it creates a session, so every run sets the configured model with `setModel` before it prompts, and sets `REVIEW_THINKING_LEVEL` along with the review skill's instructions. After each prompt the host logs `review.transcript`: the tool calls by name, the model's turns and its output tokens, counted from the session's transcript since the reset, and `activated`, the names of the skills the model activated, in call order (see Skills). A retry's counts and its `activated` include the first run's. On #23 a review approved in 19 s with nothing to show whether it read past the diff (#34). Each review starts with `session().reset()`, so earlier reviews and their large prompts don't pile up in the context or overflow it.

Phase 1 takes the review through a `submit_review` tool, whose arguments host code validates and posts, but nothing holds the model to calling it: on #5, gpt-oss-120b wrote those arguments as its final message instead (#6). So when a review run ends without a posted review, the host reads that message. A `ReviewSubmission` written as JSON, bare or in a `json` code fence, goes to `submitReview`, which validates and posts it as if the tool had been called. Anything else, or a submission `submitReview` refuses, gets one more prompt in the same session to call `submit_review`. A plain request leaves the model free to answer it in prose again, and on #16 gpt-oss-120b answered "Review submitted." without the call (#18). Forcing the call with `tool_choice` doesn't hold on Workers AI: its vLLM front end accepts a named or `required` choice and then ignores it for gpt-oss, which answered a prompt forbidding tools in prose every time. A `json_schema` `response_format` does hold, even with tools in the request. So the model's requests in that prompt carry `ReviewSubmission` as their `response_format`, through pi-ai's `samplingParams` since pi-ai doesn't model it, until the transcript has the model's answer. The retry then ends in a `submit_review` call or the review as JSON, and the host posts JSON it ends in the way it posts the first run's. Held to JSON and pressed to confirm, gpt-oss-120b wrote "Review submitted." as the summary of an approval with no walkthrough and no findings, which would have posted an approval nobody made. So `ReviewSubmission` needs at least one walkthrough entry: the host refuses that empty shell, and under the constraint the model wrote out its review instead. The retry is the model's last turn, so rejections in the JSON it ends in have no one to go back to: that review posts with the failing findings dropped, as a second submission would. A retry's JSON with walkthrough rows missing ends the review as incomplete, as a second submission does. When the first run gave the host nothing to check, because it ended in prose or in JSON that didn't fit `ReviewSubmission`, the resubmit prompt names the files that need rows. If the host still refuses that review, the summary gives the reason. If the head moves meanwhile, nothing more is asked or posted, since the review of the new head takes over. Otherwise, when nothing is posted, the summary says so and why, and keeps prose as its note. JSON never reaches the comment: text holding a JSON object counts as JSON, and what doesn't fit `ReviewSubmission` goes to the log as `review.unfit_json`. `review.done` logs `source` as `tool`, `text`, `retry` or `retry_text`, so Workers Logs shows how often the model skips the tool, which feeds #2's choice of model.

Findings are anchored by copying, not counting (#4). On #1 the model counted lines down from each hunk header, miscounted over new files a few hundred lines long, and all three comments landed on the wrong line with committable suggestions that would have broken the build. So every patch line in the prompt starts with the anchor GitHub's review API takes, `R12` for line 12 of the new file or `L10` for line 10 of the old one, and every finding quotes the text of its line. `validateFindings` compares the quote with the patch line at that side and number. A quote that carries the anchor, the diff's own marker for that side (`+` on the RIGHT, `-` on the LEFT) or an incremental review's star is compared again without them, and kept without them, because GLM-5.3 Flash sometimes copies the marker (#45). The quote as written is tried first, so a line whose own text starts like a marker still matches itself, and a quote whose readings match different lines is rejected rather than moved. On a mismatch it moves the finding to the one line on the same side of the same file whose text matches, dropping any range and that range's suggestion, since only the quoted line is verified; it rejects the finding when no line or several match. A line outside the diff is rejected rather than moved, since its number and quote most likely came from `read_file`, and a short line such as `}` would match some unrelated line of the diff. A range must lie wholly inside the diff, a suggestion is at most 60,000 characters, and a rendered comment at most 65,536, GitHub's limit, because one comment GitHub refuses fails the whole review.

A suggestion replaces the anchored lines whole, indentation included, and the model writes it like a code block in prose: on #9 every suggestion lost its line's indentation, and one restoring a deleted guard replaced the line after the deletion instead of going above it, which would not have compiled (#14). So when a suggestion is less indented than the lines it replaces, the host moves its common indentation to theirs, keeping its relative indentation; a suggestion indented further is left alone, since that may be deliberate. Then the suggestion must leave each kind of bracket, `()`, `[]` and `{}`, as balanced as the lines it replaces. When it doesn't, committing it would unbalance the file, so the host drops the suggestion and posts the finding without it, since the comment still explains the fix.

The first submission with a rejected finding, a duplicate of an open thread, a reason not to approve the host couldn't check (#122), or a changed file other than a generated or lock file that has no walkthrough row, is not posted: every rejection, every duplicate, every unchecked reason and every file without a row go back to the model together, once, as the tool's result or in the prompt that asks again. An `incremental` review needs rows only for the files it covers, and none when it only re-checks threads, since the summary keeps the stored rows of the other files. The next submission posts with whatever still fails dropped, unless files still have no row: then nothing is posted, `review.incomplete` is logged, the check run fails, and the summary comment says the review did not complete and names the files, ten at most and then a count of the rest. A blocking finding that stands rejected holds approval back: the review requests changes, and its body names the finding. A finding rejected for its basis holds nothing back, since it is unfounded rather than unposted: one with a blank basis, a `standard` or `test` finding graded blocking or major, a `defect` or `spec` finding graded suggestion or nitpick, a `standard` basis that names none of a repository standards file, a smell from `smells.md` or a repository skill the review activated (#121), a `docs` basis that names none of the pull request's docs (#125), or a `spec` finding on a pull request with no linked issue, which is rejected with the suggestion to make it a `defect` with its failure scenario if the code is wrong on its own terms. The basis is checked before the anchor, so a finding that is wrong in both ways is unfounded. `review.findings` logs the mode and the accepted, relocated, rejected and duplicate counts of every submission, how many suggestions were dropped, how many walkthrough rows are missing (`missingRows`), and the reasons not to approve it accepted and rejected (`reasons`, `reasonsRejected`). A call, or a JSON-as-text submission the host posts itself, that the host refuses before validating it, because no review is pending, the caller isn't the review in flight, the head moved or the head is already posted, logs `review.refused` with the `reason`, the pending review's `head` and `delivery` when one is pending, and `was` and `now` for a moved head, so a transcript with two `submit_review` calls and one `review.findings` can be explained afterwards (#83). In a `not_in_flight` refusal `head` and `delivery` name the review in flight rather than the caller; `callerIsRoot`, whether the caller was the root conversation, and `running`, the running root operation when one is running, say what was refused, and only a refusal `submit_review` makes before it posts carries them. `review.transcript` carries `refusedCalls`, the refusals the object counted since the review began, so a retry's count includes the first run's like its other counts; the count lives in memory, so a restart mid-review starts it again.

Tools offered to the model, all read only and `replay: "safe"` except `tree` and `grep` (see Repository search):

| Tool | Backed by |
| --- | --- |
| `get_pr` | PR metadata, title, body, labels, base and head |
| `list_changed_files` | `GET /pulls/{n}/files`, with per-file patch |
| `get_diff` | compare API for incremental ranges, `.diff` media type |
| `read_file(path, ref)` | `GET /contents?ref=`, or the head's snapshot when loaded |
| `get_issue(number)` | `GET /issues/{n}`: title, state and full body |
| `tree(path, depth)` | the head's snapshot |
| `grep(pattern, glob, path)` | the head's snapshot |
| `run_check(name, paths)` | the sandbox runs the repository's lint, typecheck or test command on the named paths and returns the exit code and the tail (#133; see Execution tiers) |

Posting is not a model tool. The model fills a structured findings document, defined with Pi Durable's `defineDoc`, and host code validates each finding against the diff hunks before anything reaches GitHub: the path must be in the PR, the line must be in a hunk on the right side and hold the text the finding quotes, severity must be one of the known values, and a suggestion must be a replacement for the lines it names. A finding that fails validation goes back to the model once, then is dropped and logged. This is the same shape the Agents docs recommend: the model proposes, your code decides.

A review has a budget in neurons, `MAX_REVIEW_NEURONS`: 10,000 by default, one day of Workers AI's free allowance, and the default when the var isn't a positive whole number. A Kimi K2.7 Code review of a nine-file pull request took 19 model calls and 48,471 neurons, nearly five days of that allowance (#99, #115). Spend is measured as the cost line measures it, by what Pi's priced `pi.usage` grew by since the baseline `pending` keeps: a model without a price adds nothing, a review that mixes priced and unpriced models counts its priced part, and one whose growth is all unpriced is never stopped. A `pending` record with no baseline, a usage the host can't read, or a read of storage that fails counts as within the budget, so a failing read never blocks a tool: the unreadable usage logs `review.usage_unreadable` with `when` set to `budget`, and any other failed read logs `review.budget_unreadable`. That ledger is Pi's total over every conversation, so a `summary` that runs beside a review adds its spend to the review's measured spend. Only a review is budgeted: the hooks act only for the root conversation and only while the operation running there is the pending review's own, its retry included, which is the test `submit_review` applies before it posts. A question is never stopped, not even one that Pi Durable starts as a follow-up when the review's run ends, while the review's record is still held, and neither is the summary session, which selects no extension and so no hook, or verify's, whose conversation isn't the root: a review that has spent its budget skips verify instead (see Verify).

The soft stop: once the spend reaches the budget, a `beforeTool` hook blocks every tool but `submit_review`, answering that the budget is spent and the model should call `submit_review` now with the findings and walkthrough it has, writing the row of a file it didn't get to from the diff, so the review ends in a shorter summary rather than a failed run. The first block logs `review.budget_spent` with the `neurons` spent, the `budget` and the `tool` it blocked. `review.transcript` counts the blocked calls as `budgetBlocked`, cumulative within a review like `refusedCalls`, and the summary's footer says the review stopped reading early, on the line after the cost line. A single read is bounded by Pi Durable's 50 KiB tool-result cap, and the number of reads by the budget.

The hard stop, for a model that ignores the block, or whose requests keep failing and being retried past it: the fourth model request made past the budget, a retry after a provider error counting as one, is refused before it reaches the model, so the run ends through `review.failed` and the summary's "did not complete" note, unless the review was posted already, which stands, since `finishReview` checks `isPosted` first. When the refused request is the retry that `askAgain` sends, the failure is still logged as `review.failed`, with `retry: true`, but the summary's note is the one that says the review couldn't be posted and that asking again failed, with the reason. The budget is not a ceiling: the request that crosses it and the three allowed past it are all spent beyond it, and the three leave room for the model's answer to the block and a resubmission after rejected findings, with one to spare. A `beforeRequest` hook can't refuse a request by throwing, because Pi Durable reports a throwing hook and skips it, so the request goes out anyway. What the hook can do is return messages, which replace that one request's and reach no transcript. So the hook on the generation task appends a marker, a user message holding `BUDGET_REFUSAL_MARKER`, to the request it refuses, and a provider wrapper in `src/models.ts`, beside the output limit's and the forced JSON's, answers a request whose latest message is the marker with an error and never calls the model. Only the hook of the root conversation adds the marker, so the two share no state. The run then settles `unanswered` as `model_error` with `BUDGET_REFUSAL` as its detail, a text that says the review's budget was spent and it didn't submit within the model requests allowed past it, and blames no tool call, since a retry counts as one of those requests. It holds no number, because Pi Durable's generation task retries an error that pi-ai's `isRetryableAssistantError` reads as transient, such as one that mentions `500` or `timeout`, and a neuron count could contain such digits. Nor does pi-ai's `isContextOverflow` read it as an overflow, which the task may answer with a compaction and a new request. The refused request stays in the transcript as an errored response, so the failed review's `calls` counts it. `review.budget_refused` logs `neurons`, `budget` and `requestsPastBudget`, the requests already made past the budget. The count of blocked calls and the count of requests past the budget live in memory and reset when a review starts, so a restart mid-review starts them again.

### Skills

The review procedure, with its severity rubric and references, the rules for answering a question, those for a summary and those for verify are Agent Skills under `skills/`, bundled into the Worker as text and fingerprinted together with SHA-256; the logs and each posted review's record carry that fingerprint beside the model id, and the summary footer shows its first eight characters as `review@…`, or as `summary@…` when a `summary` wrote the comment. Before each review, after `reset()`, the host renders the review skill and its four references into the root conversation's `instructions`, and a question carries the answer skill in its own message instead, since `configure()` takes effect at once and would swap the instructions of a review still running. A `summary` renders the summary skill and the review skill's `references/merge-danger.md` into the instructions of a session of its own, and verify renders the verify skill and the review skill's `references/severity.md` into those of another (see Verify). The Agents SDK's skills catalog, with `activate_skill` and `read_skill_resource`, serves only a repository's own skills, below. Offered those two tools, gpt-oss-120b printed its calls as raw text and never posted (#19), while GLM-5.3 Flash, the default model, called them cleanly and posted in three runs on #54 on 22 Oct 2026; on the repository-skills fixture #77, on 23 Oct 2026, GLM-5.3 Flash and Kimi K2.7 Code activated the offered skill and cited its rule, while gpt-oss-120b posted without activating it (#81). So a repository without skills gets no catalog, and the root session's tools are `read_file`, `list_changed_files`, `get_issue`, `grep`, `tree` and `submit_review`. When the request offers `activate_skill`, the preamble's tool list also names `activate_skill` and `read_skill_resource`, pointing at the `Available skills` list the catalog renders, since a model that reads only the tool list would never see them (#81). The preamble takes the names from the tools its own request offers rather than from a review flag, so a question answered after a review, while the catalog stays installed, sees them too. A summary's session offers no tool, the catalog's included. `docs/superpowers/specs/2026-10-17-skills-design.md` holds the design, the reasons behind it and the order of work.

The spec is the issues a pull request links, up to three: the closing keywords in its body (`Closes #n`, `Fixes #n`, `Resolves #n`), then its branch's `GH-n` keys, then a trailing `.n` on the branch name whose dot follows a non-digit, so a version such as `v1.2` is no key. A bare `#n` in the body counts only when none of those exists, since a pull request that mentions `#2` in passing hasn't made it the spec. With no linked issue the prompt says so and a `spec` finding is rejected, because requirements are never inferred from the code.

A repository's own rules join the review as standards (#29). After the skill and its references, the host renders the instruction files from step 1 of the pipeline as `## Repository standards`, each under a heading with its path, the most specific first: the matching `.github/instructions` files, then nested files deepest first, then the root files. The section is capped at 12,000 characters: whole files are dropped from the end, a first file longer than the cap is truncated, and a closing note names what was cut. The skill's standards check names the section, and a `standard` finding's basis names the file and the rule. The summary footer's `Standards:` line names the files used, or `none`.

One recursive trees call at the base commit lists the instruction files, and the contents API loads their bodies. The object caches both under `context:<baseSha>`, keeping from the listing only the blobs that may be instruction files and those under the three skills roots, since a whole tree can pass the 2 MB a stored value may hold. A file missing at that commit is kept as an empty body, so a later review of the same base loads only the bodies it lacks, and a new base starts from the one other record the object holds, carrying over every non-empty body of a regular file the new listing shows at the same path with the same blob sha, so a base move loads only the changed and the missing bodies; with several leftover records, or one its schema refuses, it carries nothing. A path either listing marks as a symlink (mode `120000`) is loaded again, since a symlink's blob names its target while the contents API serves the target's content, which can change under an unchanged blob. A review loads at most 24 bodies, since each one is a subrequest and the section rarely has room for more: the root files first, then nested files, which always apply, then `.github/instructions` files, which their `applyTo` may filter out; a later review of the same base loads the rest. The section still renders in the order above, and the cap still cuts from its end, whatever loaded first. A body GitHub fails to serve for any reason but a missing file is skipped, logged as `context.unreadable` with its path, and left uncached, so a later review tries it again; the other files still render. When the tree itself can't be read, the review goes ahead without the instruction files, `context.unreadable` is logged without a path, and the standards hold only `.andabot.yaml`'s matching path instructions, since the config is read on its own; with none of those, the footer says `none`. Storing the record is best effort and logs `context.uncached` when it fails. A tree GitHub truncated at 100,000 entries is used as listed. `review.start` logs the `base` and `instructionFiles`, `standardsCut`, `instructionLoadsSkipped` and `treeTruncated`.

A repository's own skills reach the review through the catalog. The same listing finds `.github/skills/*/SKILL.md`, `.agents/skills/*/SKILL.md` and `.claude/skills/*/SKILL.md`, in that order with names sorted within each root, and every blob under a skill's directory is one of its files; a path with a `..` segment or a leading slash is refused. A skill is named by its directory, so a frontmatter `name` can't pose as another skill. A skill that takes a bundled skill's name, `review`, `answer`, `summary` or `verify`, or a name an earlier root's skill already holds, is left out and logged as `skills.shadowed`. The caps read the sizes in the listing, before any fetch, and a blob the listing gives no size for is left out of the record. A skill file the listing marks as a symlink (mode `120000`) is kept in the listing but never loaded, served or fingerprinted, since its listed size and sha are its link text's while the contents API serves its target, so neither the caps nor the fingerprint could vouch for what it serves (#103). A symlinked `SKILL.md` leaves its skill out and holds no name, so a regular skill of that name in a later root is offered; the skill is logged as `skills.capped` with `cap: symlink` at its `SKILL.md` path, and none of its files is fingerprinted. A symlinked resource is left out of its skill's files and counted in a `skills.capped` event with `cap: symlink`. A skills directory that is itself a symlink is one entry with nothing listed under it, so nothing is discovered there. A record from before the modes were kept lists a symlink as a regular file until a new base replaces it. Each skill a cap leaves out is logged as `skills.capped`, naming the cap. A file over 50 KiB is never loaded: a resource that large is left out of its skill's files, and a `SKILL.md` that large leaves its skill out (`cap: file`); a file within the cap is served whole, since the catalog's tools carry output limits of twice the cap in bytes and as many lines, above the 50 KiB and 2,000 lines pi-durable cuts a tool result at by default. Skill files count bodies first, then resources, and once their listed sizes pass 512 KiB for the base, no later file is loaded or served; a skill whose `SKILL.md` lies past that is left out (`cap: base`). For a skill the catalog offers, the resources either byte cap left out, and its symlinked resources, are counted in one `skills.capped` event per cap, under `resources`. A `SKILL.md` needs frontmatter with a `description`, which the catalog lists: an empty one, or one without a description, is logged as `skills.invalid`, and a description over 1,024 characters as `cap: description`. The catalog offers skills in discovery order while their `- name: description` lines fit in 12,000 characters; the first skill whose line doesn't fit and every later one are left out (`cap: listing`).

Bodies load through the contents API into the same `context:<baseSha>` record, from the same 24 loads a review and after the instruction files, so skills never crowd out the standards. Resources load only for a skill whose cached body parses, right after the bodies when the review has loads left. A skill's own `CLAUDE.md` or `AGENTS.md` that is also a nested instruction file is fetched once a review. A skill whose body hasn't loaded yet is left out and logged as `skills.unloaded`, and a resource that hasn't loaded is missing from its skill's list; a later review of the base loads them. The bundled skills come first in `skills([builtin, repo])` from `agents/harness/pi`, marked `disable-model-invocation`, so the catalog lists only the repository's skills while a bundled name still wins, and the review skill and its references stay inline. The SDK's `activate_skill` and `read_skill_resource` return their text as `content`, but pi-durable 1.3.0 shows the model only a result's `output`, so they reached the model empty. The host now wraps every tool of the catalog to hand `content` over as `output`, leaving a result that already has an `output` alone. The same wrapping also reports each `activate_skill` call's skill name, which the object logs as `skills.activated` with the pull request's number and the review's head, and `review.transcript` lists the names in call order under `activated`, so an activation that posts no finding can be told from an over-activation of another skill (#100). The event is logged without a head when no review is pending, as for a question answered after one, or when the pending review can't be read; the list under `activated` lives in memory, so a restart mid-review starts it again. The repository's skills are a `repo` source built with `manifestSource` from the cached files, fingerprinted with SHA-256 over the sorted `path:sha` pairs of its skills' files in the base's listing, so the fingerprint is the same for every review of a base, whatever has loaded. Each review that offers a skill installs the catalog afresh, in place, after setting the instructions, so a resource that loaded since is served, and a review whose repository offers no skill, or whose tree can't be read, uninstalls it. The catalog stays installed after its review, so a later question can open a repository skill. When the object starts, the harness factory rebuilds the catalog from the stored `context:` record, so a review Pi resumes after a deploy or an eviction keeps it. The record is written only while its review still owns `pending`, so a review replaced during the load caches nothing and sweeps nothing. While a review is pending, the rebuild installs only a record whose fingerprint is the pending review's, and logs `skills.restore_skipped` with `reason: fingerprint` otherwise; with no review pending it rebuilds from the one record it holds. With several records, or one its schema refuses, it rebuilds none and logs `skills.restore_skipped` with the count and `reason: records`. A rebuild that fails is logged as `skills.restore_failed`, with the pull request's number when the object holds it, and the object starts without a catalog. `pending` keeps the repository fingerprint, the footer adds it to the skills claim (``with skills `review@06bcba08`, `repo@1a2b3c4d` ``), and `review.start` logs `repoSkills` (how many skills the catalog offers), `repoSkillsFingerprint` (its first eight characters) and `skillLoadsSkipped`. `review.tools` is logged by every review that gets through `configureReview`, once it has set the instructions and installed or removed the catalog (a review that finds nothing new to review, or is replaced first, never reaches it). Its `tools` are the names pi-durable resolves for the root session's next request, space-separated in the order it offers them, and `catalog` is true when `activate_skill` is among them, so the record shows what the model could call rather than what the review meant to install (#81). A repository without skills logs `catalog: false`; a review whose `configureReview` throws fails before the event, and a question logs none.

### Repository search

The model searches the pull request's head with `grep(pattern, glob, path)` and `tree(path, depth)` (#30). Both read a snapshot of the head commit's text files, kept in the object's SQLite in `snapshot_files`, `snapshot_left_out` and `snapshot_meta`. The first `grep` or `tree` call of a review or of a question loads it, so a review that never searches costs nothing. `GET /repos/{owner}/{repo}/tarball/{headSha}` on the base repository, with the installation token, serves private repositories and fork pull requests. The body streams through gzip decompression into a tar reader that keeps a regular file of 1,048,576 bytes or less with no NUL byte in its first 8,192 bytes, whose text decoded as UTF-8 is still within that size, since invalid UTF-8 decodes to replacement characters up to three times as long and a SQLite row tops out at 2 MB, and it skips the rest without buffering it. The reader checks each header's checksum, reads sizes and pax records strictly, and treats a stream that ends before the two zero blocks closing an archive as cut off, even at a block boundary, so a failed, cut-off or corrupt download is retried once. A path marked `export-ignore` in `.gitattributes` is missing from GitHub's archives, so the loader compares the head's recursive tree with what it kept and fetches up to 500 missing blobs of that size through GraphQL, in batches of at most 50 blobs and 4 MB (4,194,304 bytes) of the sizes the tree lists, a blob listed without a size counting as 1,048,576 bytes. Each batch is kept before the next is fetched, so the loader never holds more than one. When a batch fails, the snapshot is kept, that batch's paths are left out as `unreadable`, logged as `snapshot.gap_fill_failed` with the `error`, and the later batches still run. A snapshot holds at most 50,000 files or 400 MB (419,430,400 bytes) of text, and rows are written in batches of 200 files or 8 MB, whichever fills first. Every path the snapshot doesn't hold is recorded with its reason: `too_large`, `binary`, `lfs` (a Git LFS pointer), `submodule`, `symlink`, `gap_cap`, `snapshot_cap` or `unreadable`. A tree GitHub truncated is recorded as `treeTruncated` in `snapshot.loaded`, and the gap fill covers only the paths it listed. `tree` marks those paths and `grep` names them in its answer, so a file the snapshot lacks is never reported as a missing match. A path a truncated tree didn't list, or one past the cap, can't be named, so when the snapshot is capped or its tree truncated, every `grep` and `tree` answer, "No match" included, ends `The snapshot is incomplete (<reason>); a missing match may be in a file it didn't load.`

`grep` takes an RE2 regular expression, run on `re2js`, matched line by line over the files under `path` that match the `minimatch` glob. It answers `path:line: text` lines cut at 300 characters, at most 100 matches and 12,000 characters, with a closing note for what was left out, which names at most ten left-out files, each path cut to its last 200 characters so the note can't crowd out the matches. A file's final newline ends its last line rather than starting an empty one, so `^$` doesn't report a line that isn't there. `re2js` is linear in the text, so no pattern can backtrack: V8's backtracking `RegExp` took more than 90 s over react on patterns such as `(.\w?)*zzz` and `(.|\s)*zzz`, which `re2js` scans in about 75 ms. `RE2JS.translateRegExp` first turns JavaScript-only syntax such as `\u0041` and `[^]` into RE2's. Each line is tested on its first 500 characters only, and the answer counts the long lines it cut and warns that `$` and `\b` can match at the cut: nothing short of searching the whole line can say where it really ends, so the note is the fix (#95). Linear isn't always cheap: wide bounded repeats overflow `re2js`'s lazy DFA, which then rebuilds states on every character or hands the line to its backtracker or NFA. `.{0,400}e.{0,400}t.{0,400}[#@]{3}` took about 275 s over react with nothing to stop it. So each call has a work budget, `MAX_SEARCH_WORK`, of 750,000,000 units, charged by what the DFA does (`src/repository/regex-work.ts`): a line costs a fixed `LINE_UNITS` of 16 for the per-line work every search does, plus its searched characters plus one, plus `programSize() × (numClasses + 1)` for every DFA state it builds, since a state's transitions are each worked out at most once and each costs about the program's size. A line during which the DFA clears its cache, which is also the only way it gives up and falls back, is charged that same multiple times the states counted since the last clear plus the line's characters plus one, the characters standing in for the fallback's walk. A `^`-anchored pattern that `re2js` can run one pass at a time skips the DFA for its OnePass engine, which leaves the counters still, so a program with a non-null `re2Input.onepass` is charged `programSize()` per character plus one, plus `LINE_UNITS`, on every line. Before any engine runs, `re2js`'s prefilter scans each line for the literals the pattern needs, up to 32 scans, and nothing counts them. So the search reads the prefilter's tree once per call (`re2Input.prefilter`, declared `any`, parsed with a cyclic TypeBox schema and `Value.Check`) and charges each line, per character plus one, one unit for every Aho–Corasick scan (an OR of plain strings, walked in JavaScript at about 5.5 ns a character) after the first, and one unit for every plain-substring scan past the third (`indexOf`, about 0.5 ns a character on ordinary text, but about 7 ns on a line that repeats the needle's first character, since a short needle is found by checking every candidate position). An ordinary pattern's few scans stay free (`foo.*bar` and `import .* from ['"]react['"]` make two and three), 31 short substrings built against `indexOf`, which ran about 70 s, now stop in 4.6 s, and 32 alternation groups such as `(?:P0a|Q0b)…(?:P31a|Q31b)`, which cost about 63 s over a full snapshot uncharged, now stop in 3.6 s. The clear is seen through a mark the search puts in the DFA's `startStates` map, which a clear empties, and `stateCount` gives the states built; both are declared in `re2js`'s types, and `test/regex-work.test.ts` fails if an upgrade stops updating them or changes the prefilter's shape. Before testing a line, the call checks that the line's worst case still fits, so a call never passes the budget, and one that would stops and says how many files it searched and to narrow the path or glob or simplify the pattern. Measured with real `grep` calls under Node 22 on an Apple-silicon laptop, on ASCII text the dearest case is one Aho–Corasick scan beside four substring scans on a line built against `indexOf`, which the budget stops after about 15 s. With three substrings those scans are free, so the budget never stops them, and the 400 MB snapshot cap holds a whole snapshot of it to about 13–14 s, or about 11.5 s for three substrings alone. Every other case that spends the whole budget stopped within 3.2–6.3 s: DFA-defeating patterns on text written to be slow, the 240-empty-group OnePass pattern on code, `^[ -~]*$`, the 32-group Aho–Corasick pattern, 15–32 substrings or one Aho–Corasick scan plus 15 substrings on text built against `indexOf`, and a literal over a snapshot of empty lines. Text outside Latin-1 is dearer per unit: a pattern with many character classes, such as `\p{L}\p{N}\p{Greek}`, costs 16–21 ns a unit on CJK text, since `re2js` looks up each such character's class by binary search, but the 400 MB snapshot cap counts bytes and CJK takes three a character, so a whole snapshot of it is about 145 M units and 3 s. An ordinary or literal pattern costs about 1.55 units per character on react (56.1 M for its 36.1 M characters and 1.18 M lines), so it can search a whole 400 MB snapshot of lines that long; only patterns that build many states, and `^`-anchored patterns that run one pass at a time (`^import ` costs 392 M units on react), may need a path or glob on a large repository. RE2's `\s` matches ASCII whitespace only (`[\t\n\f\r ]`), not JavaScript's Unicode spaces. That is accepted (#95): the tool's description tells the model, and rewriting `\s` into a Unicode class can't cover `\S` inside a class, which RE2 has no way to subtract from. A pattern `re2js` can't compile, whether its syntax is one RE2 doesn't support (lookaround, backreferences) or its program is too large, is searched as literal text, and the answer says so. `patternProblem` refuses only an empty pattern and one over 500 characters. `tree` lists the snapshot's paths without reading contents, at most 500 entries, two levels deep by default; its `depth` schema has a minimum of 1, and a lower depth reaching `tree` lists one level. A review and any question answered while it runs share 40 `grep` and `tree` calls, counted until the snapshot is dropped, and a refused pattern doesn't count. They also share a run budget for `grep`'s work, `MAX_RUN_SEARCH_WORK`, of four calls' budgets (3,000,000,000 units), counted and reset with the calls, so a pull request that talks the model into repeating a dear pattern can't add calls up to a reset. `grep` checks the run's total just before it scans and adds the call's work right after, in one synchronous step, so the calls of one parallel round can't all pass the check; once the total reaches the budget, `grep` answers `Grep budget spent: this review's grep calls have searched as much as one review allows. Use tree or read_file.` without scanning. A call that starts under the budget may still spend its own whole budget, so a run's `grep` work stays under five calls' budgets, about 75 s of CPU in the dearest case measured above. An ordinary pattern can search a whole 400 MB snapshot about five times in one run, and react all 40 times. `read_file` at the head reads from the snapshot when one is loaded, and takes a path the snapshot left out from the contents API.

The snapshot lives only while it is used. The object counts the reviews and answers running, and drops the snapshot when the last one ends, so a question answered during a review doesn't drop the review's snapshot. A snapshot left behind, such as that of a review Pi resumed after an eviction, is dropped when the next review or comment starts with nothing running, or when the pull request closes with nothing running, and a load for another head replaces the old rows first. A pull request closed during a run keeps its snapshot until the run ends, which drops it as usual. Since the run count lives in memory, a review Pi resumes after an eviction isn't counted, so a close during it drops the snapshot under it. Its next `grep` or `tree` loads the head again, and since a resumed review never reaches the end that drops it, that copy stays until the object's next review or comment, as every leftover did before #93. `grep` and `tree` check that the snapshot is still there just before scanning. They search the pull request's current head, so a review that a push superseded may load or search the new head's snapshot; that is accepted (#95), since its submission is then refused, as `head_moved` or `not_in_flight`, and the snapshot it loads is the one the new review needs. They aren't replay-safe (`replay: "unsafe"`, Pi Durable's default): a scan that resets the object isn't rerun when it reopens, which would reset it again, and the model gets an interrupted result instead. `read_file`, `list_changed_files` and `get_issue` only call GitHub, so they still rerun. When the tarball or the tree can't be read, the failure is kept for the rest of the run and the tools answer `Repository search is unavailable for this review: <reason>. Use read_file.`; the review goes on. `limits.cpu_ms` in `wrangler.jsonc` is 300,000, the maximum, so loading a repository the size of vscode (8.2 s of CPU measured) and a run's `grep` work, at most five calls' budgets, can't reset the object. The logs are `snapshot.loaded` (files, bytes, what was left out by reason, gap-filled files and milliseconds), `snapshot.failed`, `snapshot.dropped` (reason `review_end`, `answer_end`, `stale`, `closed` or `new_head`), `snapshot.drop_failed` and `snapshot.gap_fill_failed`; `review.done` carries `greps`, `trees` and `grepWork`, the run's `grep` units. `docs/superpowers/specs/2026-10-22-repository-search-design.md` holds the measurements, the choice of a tarball over a clone and the reasons behind the rest.

### Review pipeline

1. Gather: changed files, patches, PR body, the repo's config file, and the instruction files the repo keeps for agents, read at the pull request's base commit so that a pull request cannot change the rules it is reviewed by: `CLAUDE.md`, `AGENTS.md`, `REVIEW.md`, `CODING_STANDARDS.md`, `.github/copilot-instructions.md` and `CONTRIBUTING.md` at the root, each `.github/instructions/*.instructions.md` whose `applyTo` matches a changed file or that has no `applyTo`, and a `CLAUDE.md` or `AGENTS.md` in any directory above a changed file; and the repo's own skills under `.github/skills/`, `.agents/skills/` and `.claude/skills/`, at the same commit; and the repository's authoritative docs (#125): the changed ones the review checks, and the lines of the head's docs, read from its snapshot, that name a changed file, apart from a changed doc's own changed lines.
2. Draft: one pass over the diff, in chunks sized to the model's context, producing candidate findings and a per-file walkthrough.
3. Verify (#31): a second pass takes every finding but nitpicks about to post, with the exact lines it cites and the code around them, and keeps or drops it and sets its severity from what the code shows. This is what makes cheaper models usable; unverifiable findings are the noise people leave CodeRabbit over. It runs in a session of its own, after the final submission validates and before the review posts, and only when verify is on: `VERIFY_MODEL` names a model and the repository hasn't turned it off. See "Verify" below, and `docs/superpowers/specs/2026-10-24-verify-design.md` for the decisions behind it.
4. Post: edit the summary comment in place, submit one review with the inline comments, set the review event, from the verified findings, by the approval policy below, where an approval waits for the head's other checks to pass, and complete the check run, in progress since step 1, with the verdict in its title. A review that does not complete fails it.
5. Record: `reviewed`, a `finding:<commentId>` per inline comment, the review id.

Reviews follow CodeRabbit's model (#24). A push reviews only what changed since the last review. A push never repeats an open thread, and it resolves the threads it fixed. `full review` starts over. Each review runs in one of three modes, chosen before the prompt:

- **`fresh`**, on `@andabot full review`, is the whole pull request as before: no thread lists, no duplicate check and no resolving. Its event follows this review's findings and andabot's open blocking threads, which it reads for that alone, so a full review never approves past one (#25).
- **`full`**, on a push with no `reviewed` record, a retargeted base, a failed compare, or any compare status but `ahead` or `identical`, is the whole pull request too, but it never repeats an open thread. `diverged` and `behind` mean rewritten history. The first push to each pull request after this shipped is `full`, so it doesn't repost every existing finding.
- **`incremental`** reviews what changed since the last review. It covers the pull request's files whose own changed lines the compare `reviewed...head` also changed, so a merge from the base branch drags nothing in.

In `incremental` mode, the prompt shows the pull request's own numbered patch for each covered file, with the lines that changed since the last review starred after their anchors (`R12*`). A file with a thread to re-check but no starred line gets the compare's patch instead, unnumbered, under "New changes outside the diff", so the model can see that the push deleted or reverted the flagged code. It lists the other files by name only. A file the push changed without a starred line is listed as "changed since the last review, with no line to comment on" rather than "unchanged", and the walkthrough keeps any row the model writes for it. Such a file may be binary, too large for GitHub to diff, or one whose new changes all left the diff (#45). Those rows stay optional, so the coverage check never ends a review over a binary file.

- **Why marked lines are the PR's own.** Comments anchor to the pull request's diff, not to the compare's, so marking that diff's lines keeps every anchor one GitHub accepts. RIGHT lines are marked by number, since both diffs number the head the same way, and only the pull request's own `+` lines are marked: a context line the compare added is the base's change, merged in. LEFT lines are marked by text, since their old-file numbers differ.
- **What a finding may anchor to.** A finding must sit on a marked line, except a blocking one: a bug the push causes in code it didn't edit, such as a caller of a changed function, still gets an inline comment if its line is in the diff.
- **When there's nothing to review.** When no line is marked and no thread is due a re-check, there is no model call. The check run completes as "No changes to review since `abc1234`". A push whose changes all left the diff, such as deleting a line the pull request added, has nothing to comment on, so it is reviewed only through the threads it touched.
- **An unchanged head.** `identical`, a head already reviewed, takes the same path, so a redelivered push isn't fully reviewed again.

Both `incremental` and `full` reviews fetch the bot's open threads from GitHub's GraphQL `reviewThreads` and list them for the model in two groups, with handles (`T1`, `T2`, …):

- **The threads to re-check.** In `full` mode, these are the threads GitHub marks outdated. In `incremental` mode, they are the threads on a marked line, the outdated threads whose quoted line the push added or deleted in that file, and, since #123, every open thread of andabot's in a file the push changed or in a file whose test file the push changed (a test file is one under `test`, `tests`, `__tests__` or `spec`, or named `.test.` or `.spec.`, and it matches a thread's file when their stems agree: `test/cost.test.ts` for `src/review/cost.ts`), judged against the new commits only and under the same cap of 30. For a thread with no stored quote, any change to its file counts. Deleting the flagged line, the most common fix, re-checks its thread; so does a test added further down the file, which #60's author had to resolve by hand. A caller fixed in another file is still missed. Before the review resolves the threads the model listed as addressed, it reads the pull request's threads once more and leaves out one already resolved, logging `review.resolve_skipped` (`number`, `thread`), so a thread the answer session closed meanwhile gets no second reply.
- **The other open threads** are listed so the model doesn't repeat them.
- **Duplicates.** A finding is set aside as a duplicate when it sits on an open thread's line, or quotes the code of an outdated one (whose line GitHub no longer reports). A thread that isn't outdated still has its line, so a common line such as `}` elsewhere in the file is no repeat. The check runs against every open thread, listed or not. A blocking finding on the line of a thread that isn't blocking still posts, since that thread doesn't gate approval. Like other rejections a duplicate goes back to the model once, but it doesn't hold approval back, since the open thread already does.
- **The cap.** The lists hold at most 30 threads, newest first, with the threads to re-check ahead of the rest. A note counts the threads left out.

The model names the threads it fixed in `addressed_threads`. Only the bot's own unresolved threads are touched:

- **Before the review is chosen,** the host resolves each named thread with `resolveReviewThread`, best effort, like the check-run calls. The event then counts only the threads that resolved.
- **After the review posts,** it replies "Fixed in `def5678`." on each one that resolved. A publish retried after a failed `createReview` resolves again, which is harmless, but never replies twice.
- **Approval.** Such a review never approves while one of the bot's blocking threads stays open, counting every open thread, not only those listed. If the threads couldn't be read, it never approves at all. Neither does it when a pull request has more than the 500 threads the query pages through, since an incomplete count could miss a blocker.

The summary comment keeps the summary and walkthrough of the last full review, or of a later `summary`. An incremental review replaces the walkthrough rows of the files it covered and adds a "Since `abc1234`" section, whose text is the submission's `changes_since`, what the new commits do (the model's `summary` keeps describing the pull request; a submission without `changes_since` is refused once and then posted with the summary as the text, logged as `review.changes_since_missing`), with every thread handle the prompt listed (`T1`) rewritten as a link to the thread, titled by the thread (#126). The merge danger under the verdict is the pull request's, from the last full review or `summary`: a push's judgement describes the new commits alone and is shown in the Since section as "This push: two-way door · docs only."; the pull request's line changes only when a one-way push escalates a two-way door, and then it takes the push's radius (#124), so a docs-only push can't make the whole pull request read as harmless. The review's body says what it covered: "Incremental review of `abc1234..def5678`: 3 files; 2 threads resolved." or "Full review.". `review.start` logs `mode`, `since`, `covered` and `recheck`; `review.resolved` and `review.skip` (`no_new_changes`) say what happened.

A `summary` (#27) replaces the stored summary, walkthrough and merge danger with ones written for the current head, and drops the "Since" section, which the new summary covers. Its walkthrough rows replace the stored ones, a changed file it left without a row keeps its stored row only while the base's `path_filters` leave that file in, since only the files they leave in count as changed here, and the merge danger is replaced outright, as a full review's is, rather than kept across a push as an incremental review keeps it. `reviewed` keeps the head of the last review, so the next incremental review still diffs from what was reviewed, and a review that posts later builds on the new summary as on any stored one. With no `reviewed` record, `summary` only rewrites the comment, since a record would make the next review incremental from a head nobody reviewed. The verdict line stays the last review's, with its verdict and counts as they stand, a later "Approved at `abc1234`" included, and it names that review's head when the summary describes a newer one, as "Changes requested at `abc1234`" under the head `def5678`, so an old verdict never reads as a judgement of a newer head. The line comes from the stored records rather than the comment's text, since a failed review's comment has no verdict and the records outlive it: `last_review`'s shown verdict and counts, so "Approval waits for the checks", stored as a `COMMENT`, reads as itself again. A `last_review` written before #27 has neither, so its line shows the event alone, with no counts. Before any review the line reads "Not reviewed yet", and on a pull request last reviewed before `last_review` existed, "Not recorded". While a pull request is paused, every render of the comment carries the paused line that "Commands and chat" describes.

### Verify

Verify (#31) is a second model pass over the findings a review is about to post. The audit of all 146 of andabot's findings, recorded on #31 on 21 Oct 2026, found 10 of the 58 on real pull requests false and about 19 graded at the wrong severity, and two of those cases crossed the blocking line, which decides whether a review requests changes or approves: #9's harmless missing `await` was graded blocking 11 times, and #49's real defect a suggestion. So verify's main target is severity at the blocking line, its second is dropping false findings, and its hard rule is that it never drops or demotes a true blocking finding. A model is picked only if, scored on a replay set of the audit's labelled findings in three runs, it demotes #9's `await` and promotes #49's defect, drops at least half of the eligible real false findings, and in no run drops or demotes a true blocking finding. Four of the eight named false findings were nitpicks, which verify never sees; Andrew set the eligible drop bar at two of four. The 24 Oct replay showed GLM breaking the hard rule and missing severity targets, and Kimi missing all three required `await` demotions in its first two complete runs. Kimi's third run stopped at the agreed spend cap, but one remaining run could not meet their two-of-three majority. `VERIFY_MODEL` therefore stays empty. `docs/superpowers/specs/2026-10-24-verify-design.md` holds the decisions, the replay set and its scoring; [#31 records the measurement](https://github.com/ItsAndrewM/ai-review-agent/issues/31#issuecomment-6389469628).

`VERIFY_MODEL` in `wrangler.jsonc` is the default verify model. Empty, it turns verify off everywhere, whatever a repository's `.andabot.yaml` says, so a repository can't turn on a model before its cost has been seen. With a model set, a repository's `model.verify` names the model it uses instead, and `reviews.verify: false` turns verify off for it (see "Configuration file"). The review resolves both when it starts and keeps the result on `pending` as `verifyModel`, beside the request-changes workflow and the config error, leaving it out when verify is off. An `.andabot.yaml` that is invalid or unreadable applies none of its settings, so its `reviews.verify: false` is ignored while `VERIFY_MODEL` is set.

What verify judges and may change:

- **Candidates.** Every accepted finding but nitpicks (blocking, major and suggestion) in the submission about to post, and every blocking finding that was rejected but still holds approval back: one rejected for something other than its basis or the path filters, such as an anchor that doesn't hold or the cap of 25 findings. A false one of those blocks the pull request all the same. The candidates are numbered `F1` to `Fn`, the accepted ones first. Nitpicks, open threads, the model's `addressed_threads` and findings rejected for their basis, which hold nothing back already, never go to verify.
- **Verdicts.** One per finding id: keep or drop, a severity in either direction (`blocking`, `major`, `suggestion` or `nitpick`; a revision that would break a basis pairing is kept at the draft severity and reported as capped) and a one-line reason of at most 300 characters. Verify never rewords a finding, edits its suggestion, changes its basis or adds a finding. The verify skill tells the model to drop a finding only when the code shows its claim wrong, and to keep it at its draft severity when its tools can't settle the matter, which is how the hard rule is meant to hold.
- **The basis cap.** The host's basis rules still apply to the severity verify returns: `pairingProblem`, which `validateFindings` shares, tests each revision in both directions. A `standard` or `test` finding can't be blocking or major, and a `defect` or `spec` finding can't be a suggestion or a nitpick. A revision that breaks the pairing, promotion or demotion, is ignored: the finding keeps its draft severity and its verdict is logged as `capped`. Rejecting it as unfounded instead would drop a finding verify meant to keep.
- **The delta rules.** Verdicts apply to the validated review, and the push's delta rules (`applyDeltaPolicy`) then run again on the result. Two of them favour a blocking finding: in an incremental review it may sit on a line the push didn't change, and on the line of a non-blocking open thread it isn't a duplicate. A finding that got in only through one of them is left out once verify demotes it, as a non-blocking finding in that place would be, and the summary comment's Verify section lists it as demoted and left out. A held back finding that verify demotes stays rejected and no longer holds approval back; one that verify drops is removed. A finding with no verdict was not judged and posts as drafted. A verdict for an id that isn't a candidate is ignored, and so is a second verdict for one id: the first wins.
- **The event.** The review's event is derived after verify by `decideReviewVerdict` from the verified findings, held back ones included, the open blocking threads and the reasons not to approve (#122): a finding verify promotes to blocking makes the review request changes, and one it clears lets the review approve, wait for the checks, or withhold approval by the reasons alone. The model submits no verdict, so there is nothing for verify to reconcile.

How a verify run goes:

- **Placement.** In `postReview`, after the final submission has validated, which is after the one round that sends rejections back to the model, and before the review publishes, on the tool path and on the JSON-as-text path alike. Reviews post from inside `submit_review`, so on the tool path that call waits for verify. A review with no candidate skips verify and says nothing of it.
- **Budget (#115).** If the review's measured spend has reached `MAX_REVIEW_NEURONS`, verify is skipped: `verify.skip` is logged and the review posts unverified. Otherwise verify runs. Its conversation isn't the root, so the budget's tool and request hooks don't gate it, and its spend joins the ledger the budget measures, as a summary's does.
- **Session.** Verify has a Pi session of its own, which `verifySession` names, created and stored as `summarySession` is. Each attempt resets it and configures it with the verify skill and the review skill's `references/severity.md` as instructions, `REVIEW_THINKING_LEVEL`, the verify model through `setModel`, and the verify extension's four tools: `read_file`, `grep`, `tree` and `submit_verdicts`. A new review resets it too, so the cost line never counts an earlier review's verify calls.
- **Isolation.** Pi Durable selects an extension by name from the registry, so the verify extension has to be installed in it. The settings' default selection is then every installed extension except verify's (`withoutVerifyByDefault`), so the root conversation keeps the tools it had and chat never sees verify's. Left in the default selection, `submit_verdicts` reached the root and verify's `read_file` shadowed the review's.
- **Prompt.** One prompt holds every candidate under its id: its path, lines, side, severity, basis kind, title and quote, then its basis and body, then its cited window. The window is the cited lines and about 40 either side, read at the head or, for a `LEFT` finding, at the base, and numbered as `read_file` numbers them; a file that is missing at that ref or can't be read gives "file unavailable", and a failed read is logged as `verify.file_unreadable`. A held back candidate carries a line saying it couldn't be placed inline, so verify judges its claim on the code and not on whether its quote is in the window. A `## Patches` section shows each cited file's patch once, cut at the review prompt's limit of 40,000 characters per file, and a `spec` finding also gets the linked issues' text, with `verify.issue_unreadable` logged for one that can't be read. It all sits in the data block a review's prompt uses, with its closing tag neutralised.
- **Tools.** At most 10 calls of `read_file`, `grep` and `tree` in an attempt; the rest answer that the budget is spent. Verify's `grep` and `tree` also count toward the 40 that a review and the questions answered during it share, since verify runs inside the review.
- **Answer.** Taken from `submit_verdicts`, read once the prompt has settled. A JSON-as-text answer, bare or in a `json` fence, is the fallback. An empty list of verdicts, or an answer that doesn't parse, fails the attempt.
- **Concurrency.** `submit_review` runs one call at a time (`executionMode: "sequential"`), so two calls in one tool round can't overlap, and only one verify run holds the verify session at a time. Each run's operation ids are `<review operation>:verify:<run>:<attempt>`, with a fresh random `<run>`, so Pi's id dedupe can't hand a later run in the same review the stale answer of an earlier one. Those ids begin with the review's own, so the single flight counts them as the review's. It asks the harness for the root session's operations and for verify's separately, and on a newer push aborts verify's first, each in its own session, since the root's `submit_review` call is waiting on verify. Each attempt restarts the grace first, which keeps the gap between attempts from making a live review look dead. Which run holds the session lives in memory, so after a restart the tools of a verify run Pi resumes answer that no verify pass is running.
- **Failure.** Verify has no time cap beyond a backstop of 15 minutes for each attempt. An attempt fails when the model call fails after Pi's own retries, when the run ends unanswered, when the answer is unusable or empty, or when it passes its backstop. A failed attempt is retried once, as a fresh attempt with its own backstop, so the worst case is 30 minutes, and the operation of a stalled attempt is aborted before the retry starts. If both attempts fail, the review posts the draft's findings as drafted, marked unverified, and `verify.failed` is logged. A model id Workers AI doesn't serve fails the model call, so it is a verify failure, not a config error.
- **After verify.** Verify can take minutes, so before the review publishes it reads the pull request's head again and checks that it still owns `pending`. If the head moved or the review was replaced, nothing is posted: the call is refused as `head_moved` or `not_in_flight` and logged as `review.refused`.

What the pull request shows:

- **Inline comments** show the final severity, with no note about what changed.
- **The summary comment** gets a collapsed Verify section listing each drop (path, line, title and reason), each severity change (the path, line and title, then from → to, ", left out" when the delta rules set the finding aside, and the reason) and each finding verify didn't judge. It is left out when verify dropped nothing, changed no severity and left nothing unjudged, since the footer already shows that it ran. A capped verdict changes nothing, so it isn't listed.
- **The footer** reads "Reviewed by `M` · verified by `V` with skills … in 34.8 s", the seconds being the review's elapsed time from the record (#50; a record from before the field prints no time). An unverified review reads "Reviewed by `M` with skills …" and then gives its reason on a line of its own, "Not verified by `V`: the model call failed.", or "no usable answer", "no answer in 15 minutes" or "the review spent its budget" in its place; a failure's full reason is in `verify.failed`. The cost line includes verify's spend and calls. The calls are counted from the verify session's transcript, which each attempt resets, so a retried verify counts only its last attempt's calls, while its tokens and cost, read from the ledger, include both.
- **The check run's title** ends " (unverified)" when the review is unverified. `PostedReview` stores the flag, so a later run of an already-posted head keeps it.

The logs are `verify.start` for each attempt (the number of candidates, the model and the attempt); `verify.verdict`, one for each verdict (the finding's id, path and line, `keep`, the severity from and to, `capped`, `ignored` for an unknown or repeated id, and the reason); `verify.done` (the counts kept, dropped, promoted, demoted, capped, not judged and unknown, the milliseconds and the attempts); `verify.attempt_failed` for each failed attempt, with its reason, so the first failure isn't lost when the second attempt succeeds; `verify.failed`, with the full reason, the milliseconds and the attempts; `verify.skip` when the budget is spent (the neurons and the budget); and `verify.file_unreadable` and `verify.issue_unreadable` for a cited file or a linked issue that couldn't be read. All carry the pull request's `number`, and all but the last two its `head` and the verify `model`.

### Approval state machine

`evaluateApproval` decides whether to approve the current head without a push (#25). It runs when a thread is resolved or unresolved, when a check suite other than andabot's finishes, after `resolve` and on `resume` (#27), after a posted review that didn't approve, except one that just posted a blocking finding, whose thread is certainly open and may not show in GitHub's list yet, and when a push or a ready-for-review event on an open pull request that isn't a draft finds its head already reviewed, so a draft reviewed under `reviews.drafts` gets its waiting approval once it is marked ready. It makes no model call. `decideApproval` in `src/review/approval.ts` is a pure function of what the object reads live, and it waits for the first of these that holds:

1. `workflow_unknown`: the last review was recorded before the record kept its workflow, or there is none, and `.andabot.yaml` at the pull request's base can't be read. Unknown means wait, as with the threads and the checks, never a fall back to the Worker var.
2. `workflow_off`: the request-changes workflow is off. It is the one the last review ran under, kept on `last_review`; for an older record or none, `.andabot.yaml`'s `request_changes_workflow` at the base, or `REQUEST_CHANGES_WORKFLOW` when the file doesn't set it.
3. `paused`, whatever triggered the evaluation, so during a pause only a review's own event can approve. `resolve` resolves the threads but leaves approval to `resume`, and a review whose approval waits for the checks gets it only after `resume`, even when the checks pass during the pause. `resume`'s evaluation lets through what the pause held up.
4. `not_open`: the pull request is closed, merged or a draft.
5. `review_in_flight`: a review is pending. It evaluates when it ends.
6. `not_reviewed`: the head isn't the reviewed head.
7. `no_record`: there is no `last_review`, as on a pull request last reviewed before this shipped.
8. `approved`: the last review is an approval, of this head or an earlier one, so a push with nothing new to review brings no second approval.
9. `review_stands`: the last review held back a blocking finding it couldn't post inline, which no one can resolve, or carried a reason not to approve (an omitted requirement, a not-for-merging line, a budget cut), whatever its event, or was an older comment without an `approve` verdict. Re-evaluation lifts a request for changes that carried no reason, and an approval held back only by unreadable threads or unfinished checks. It never turns a withheld review into an approval: the next review decides.
10. `threads_unknown`: the threads couldn't be read, or there are more than the 500 the query pages through.
11. `blocking_threads`: one of andabot's blocking threads is open.
12. `checks_unknown`, `checks_failing` and `checks_pending`: the head's check runs other than andabot's couldn't be read, one completed with a conclusion other than success, neutral or skipped, or one hasn't completed.

Otherwise the object re-fetches the head and, if it hasn't moved, submits `APPROVE` on it with a short body, records it as `last_review`, rewrites the summary comment's verdict to "Approved at `def5678`", marks the head's posted record as shown approved and retitles the review's check run (whose id the posted record keeps) to "Approved: 1 suggestion, 2 nitpicks" with the review's counts, Details still opening the summary comment; a record without an id or a failed update is logged as `approval.check_run_failed` and skipped (#126). A later failing check or a reopened thread doesn't revoke the approval, and the next review of a new head decides again. A thread event and a check event can arrive together, so an in-memory mark per head keeps the second from approving too.

A review's own approval waits for the checks as well. When `decideReviewVerdict` would approve, the host reads the head's check runs first. Unless they pass, the review posts as a comment, its summary and check run say "Approval waits for the checks", and the evaluation approves once they pass, since that review's `last_review` records the shown verdict as awaiting the checks. A clean head whose checks finish after its review gets two reviews: the comment, then the approval.

The host derives the verdict; the model submits none (#122). Findings carry one of four grades (#121): blocking, when merging ships a wrong result, data loss, a security hole or a spec departure that a user of the change meets; major, a real defect whose reach is bounded, worth fixing but not blocking; suggestion, an improvement to code that works as it stands; and nitpick, style and naming. A `defect` or `spec` basis pairs with blocking or major, a `standard`, `test` or `docs` basis with suggestion or nitpick, and a `standard` basis must name a file under `## Repository standards`, a smell from `smells.md` or a repository skill the review activated (kept on the `pending` record as `activated`); validation refuses the rest as unfounded, and verify keeps a revision that would break a pairing at its draft severity. The event: a blocking finding, posted, held back or in an open thread, requests changes; otherwise the review approves, waiting for the checks as above, unless it carries a reason not to: a requirement of a linked issue the diff leaves out (`omitted_requirements`, each checked against the linked issue numbers), a line of the title or description that asks not to merge (`not_for_merging`, checked as a quote), or a review the budget cut short. A reason posts the review as a comment shown as "Approval withheld", with a "Not approved because:" list in the review body; a reason never requests changes, since no thread can resolve one and a hallucinated omission must not red-mark a pull request. The reasons stick: `last_review.withheld` counts them, and the re-evaluation never lifts a review that carried one, so fixing the blocking findings on a not-for-merging pull request waits for the next review. An incremental review lists the last review's omitted requirements under "Reasons to re-check" in its prompt, so a trivial push can't turn a withheld head into an approval by silence; the `reviewed` record keeps them. The decisions are in `docs/superpowers/specs/2026-10-29-reviews-that-hold-up-design.md`, slice 4.

The review checks the docs against the code (#125). The host knows which files are docs: `reviews.docs` in `.andabot.yaml`, defaulting to READMEs at any depth, `docs/**/*.md` and the instruction files; `docs/superpowers/**` is history and is never checked unless the pull request adds the file. The prompt's data block lists the changed docs under `## Docs under review` (an added plan or spec with a note to check only its claims about this pull request's changes), and under `## Docs mentioning the change` the `path:line` lines of the head's docs, read from its snapshot through the repository search and its work budget, that name a changed code file by path or by basename (a doc under review is searched too, apart from the lines the push added, which its own check covers) (six per changed file, forty in all; a short or common basename such as `index` is searched by path only). A claim the code contradicts is a `docs` finding, suggestion or nitpick, whose basis names the doc's `path:line` and the claim and the contradicting code `path:line`; the host refuses one that names none of the pull request's docs (the head's docs minus history, plus the changed ones, kept on the `pending` record as `docs`). A false claim in a changed doc anchors on the doc line; a stale doc for changed code anchors on the changed code line. In an incremental review the push's covered files are sorted and searched. `review.docs` logs `under`, `history`, `code`, `mentions`, `mentionFiles`, `overflow` and `search`. The decisions are in the same spec, slice 6.

A head with no check runs besides andabot's passes, so a repository without CI can be approved. Just after a push that is a race, because CI hasn't created its first run yet (on #46 it appeared 9 s after the push), so a push with nothing new to review doesn't evaluate, and CI's suite completion does later. The window that's left is accepted: a thread resolved within seconds of such a push, or a review that ends before CI creates its first run, can approve a head whose CI then fails. The evaluation a ready-for-review event runs on a draft reviewed under `reviews.drafts` has the same window when the repository's CI skips drafts and starts only once the pull request is ready: it can see only the draft's finished or skipped runs.

After a catch-up review that finds nothing new to review, `resume` evaluates all the same. Pushes that add no line to the diff, such as a merge from the base branch, end that review as "No changes to review", and the thread and check evaluations that arrived during the pause were dropped, so without one an approval the pause held up would wait for some later event. Those pushes came during the pause, so CI has most likely started; the window left, a push in the seconds before `resume`, is the kind accepted above.

GitHub sends one completion per check suite, so for that suite the evaluation it starts is the last chance. When that evaluation can't settle, the object checks again instead of waiting for an event that won't come (#86). On #74 the event reached the object while the review was posting, so it waited as `review_in_flight`. The evaluation that review ran after posting read GitHub's check-runs list 17 seconds after GitHub had announced the run complete. It still saw the job unfinished and waited as `checks_pending`, and nothing evaluated again until CI was re-run four hours later. GitHub had an Actions incident at the time, but nothing promises that the list keeps up with the event.

So when an evaluation triggered by `checks_completed` fails, or waits as `review_in_flight`, `checks_pending`, `checks_unknown`, `threads_unknown` or `workflow_unknown`, it pushes a Lifecycle job, `approval.recheck`, which the host's `onJob` runs. That job evaluates again 20 seconds later with the trigger `recheck`. A re-check that can't settle either pushes the next one, a minute later and then five, and the third is the last. The job is durable, so a deploy or an eviction doesn't drop it. It has one id per pull request, so a later suite's completion restarts the chain instead of adding a second. A later completion can arrive while a re-check is reading GitHub. So right before a re-check pushes the next attempt, it reads the job's delivery, with no await between the read and the push. When that delivery is a newer chain's, the re-check stops with `approval.recheck_yielded`, so a later attempt can't replace the newer chain's first re-check. Every other answer ends the chain, the approval and `approving` included. No other trigger starts a chain: after a review, a thread event or a command, any check suite still running sends its own completion. A re-check that runs after the approval posted finds it `approved`. One that finds a new head evaluates that head as any event would. A job the host can't read is dropped with `job.unreadable`.

Rules copied from CodeRabbit's workflow: approve only when the latest commit has a completed review, every blocking bot thread is resolved, no check fails, and the head is unchanged at the moment of approval. An optional finding never blocks; only findings marked blocking open threads that gate approval. Only check runs count, not commit statuses, and a fork's check events can't be routed, since GitHub sends them with no pull request. Branch protection keeps one human approval required regardless, and GitHub's "code review limits" setting must allow the App to submit approving reviews.

The evaluation logs `approval.decided` with its trigger (`thread_resolved`, `thread_unresolved`, `checks_completed`, `review`, `already_reviewed`, `resolve`, `resume` or `recheck`), the head and the reason it waited, `approval.posted` with the review id, and `approval.checks_failed`, `approval.summary_failed` and `approval.failed` when a read or a write fails. A scheduled re-check logs `approval.recheck_scheduled` with its attempt, its delay and the delivery of the suite completion that started the chain. A re-check that leaves the job to a newer chain logs `approval.recheck_yielded` with its own chain's delivery and the newer one's. It returns its outcome, the approval, the reason it waited or a failure, so `resolve` can say what approval does next.

### Commands and chat

`@andabot <command>` in an issue comment, a review comment or a review's summary, which is answered in the conversation. The App's login is `andabot[bot]`; GitHub resolves the mention `@andabot` to it. Commands: `review`, `full review`, `summary`, `resolve`, `pause`, `resume`, `help`. Anything else is a chat turn in the PR's root Pi session, which already holds the review transcript, so "why is this a problem?" on a thread works without re-reading the PR. Replies to a review comment go back on that thread. In one of andabot's own threads the chat turn can close the thread (#123): the prompt names the finding's severity and title and the head's sha, the answer skill (version 2) says to read the head when the reply claims a fix or argues the finding away, and the root session's `resolve_thread({ reason: "fixed" | "withdrawn", evidence })` tool resolves the thread the turn is answering in, never one the model names. The host refuses a call without evidence (the head's `path:line`), one made outside an answer in one of its threads (the guard is the root session's running operation being the answer's own, since a reply queued behind a review runs in the same conversation), one for a thread already resolved by the review, and one GitHub can't be reached for, which the model is told to report as still open; a second call in the same answer is told the thread is already resolved by this answer. The model's text is the one reply, posted after the tool ran; a reply on a thread the review resolved meanwhile is dropped and logged `answer.skipped` (`number`, `thread`, `reason: thread_resolved`); after the reply the approval is re-evaluated with the `resolve` trigger. The logs are `thread.resolved` (`number`, `thread`, `reason`, `by: answer`) and `thread.resolve_failed`. Andrew's rulings (29 Oct 2026): andabot verifies a claimed fix right then rather than leaving it to the next push; the model decides what a claim is, with no pattern on "Fixed in"; evidence is required for every severity; one reply per thread is kept by reading before resolving, not by new state.

A reply in a review thread whose first comment is andabot's is a question about that finding and needs no mention; in any other review thread, `@andabot` asks. The router passes every review comment that mentions the bot or replies in a thread, and the object looks the thread up through GraphQL `reviewThreads` to tell whose it is. The answer's prompt carries the thread's file, line, diff hunk and opening comment, and the answer goes under the thread's first comment, since GitHub takes replies only to a thread's top-level comment.

Only users with write access to the repo can issue commands; the object checks the commenter's permission before acting.

A comment that passes that check gets a 👀 before andabot acts on it, so whoever wrote it sees andabot is on it. The 👀 means a reply or a review follows, so a comment andabot ignores gets none, and neither does an edit, since andabot reads only new comments. A command bypasses the `.andabot.yaml` settings that skip a push, `resume` aside, which reviews as a push would, so only `path_filters` that leave out every changed file can stop its review, and then the reply says so. A `review` with nothing to do says why: the head was already reviewed, with a pointer to `full review`, the pull request is closed, or the filters leave nothing to review. One that finds a review already running for the head, or the head moved, says nothing, since that review posts. The reaction is GraphQL `addReaction` on the comment's node id, which works for a review's summary too, where REST has no reactions endpoint. The object logs `reaction.added`, or `reaction.failed`, which never stops the command. A pull request whose description tags andabot gets a 👀 when it opens, from anyone, since a review follows unless the repository's `.andabot.yaml` skips it (`auto`, `drafts`, `base_branches` or a title keyword, or `path_filters` that leave out every changed file), and a skip is logged as `review.skip`. The reaction stays in the router, which never reads the file, so a pull request the file skips keeps its 👀 with no review. An untagged description gets none, as the review's check run already shows andabot at work.

A command is the whole text after the mention, trimmed, in any case, so "pause please" is a question. In a review thread a command needs the mention too, since a bare reply in andabot's thread is a question, and it replies under the thread's first comment; anywhere else it replies in the conversation. `help` lists all seven commands, one line each. The summary comment's footer lists only `review`, `full review` and `help`, whether a review or a `summary` wrote it, since all seven would crowd every summary.

`pause` (#27) stops what andabot does on its own until `resume`: the reviews that `pull_request` `opened`, `reopened`, `ready_for_review` and `synchronize` start for the pushes `.andabot.yaml` would otherwise review, and approval by the evaluation, which waits while paused. Whatever a person asks for still runs: `review`, `full review`, `summary`, `resolve`, and chat and thread answers. A review from a `pull_request` event carries no `requestedBy`, while one from a command or a check's re-run does, so `review()` first skips a review nobody requested on a paused pull request, before any GitHub call, the read of `.andabot.yaml` included, and logs `review.skip` with reason `paused`. A push during a pause leaves no andabot check run on its head, which holds nothing up, since andabot's check isn't a required one. A review requested during the pause is a normal review, and a review already running finishes and posts; each one's own event can approve. `pause` writes `paused` and `pausedBy` together, logs `command.paused`, adds the paused line to the summary comment, and replies "Paused: pushes won't start reviews until `@andabot resume`.", or "Already paused." when it is. It acts on a closed pull request as on an open one, as `resolve` does.

The summary comment says so at once. `pause` puts "⏸️ Paused by @user: pushes don't start reviews. `@andabot resume` to resume." under the comment's header, ending in the hidden marker `<!-- andabot:paused -->`, and `resume` takes it out. Both edit the comment in place, adding or removing that one line and leaving the rest as it stands; with no summary comment yet, `pause` creates one with the header, the head, the line and the note "Not reviewed yet." Every other render of the comment while `paused` is set, by a review, a failed review or a `summary`, carries the line too. A line counts as the paused line only when it starts with "⏸️ Paused" and ends with the marker, so a line of a summary that quotes the marker, as a review of this repository can, is never taken for it and removed. A failed edit is logged as `command.summary_failed` and leaves the flag as set.

`resume` on a pull request that isn't paused replies "Not paused." and does nothing else. Otherwise it reads the pull request fresh, deletes `paused` and `pausedBy`, takes the line out of the summary comment, and replies with what it does next before it does it. The read comes first, so one that fails leaves the pull request paused for another `resume`. A closed pull request gets nothing more. When a review of the head is already running, `resume` says so and leaves the head to it. It counts a review as running only while the single flight would turn a new one away, while Pi lists one of its operations or its record is within the grace, so a dead record doesn't stop the catch-up review. Otherwise a head already reviewed, the reviewed head or one with a `posted:<sha>` record, gets the approval evaluation with the trigger `resume`, so an approval the pause held up can go through: "Resumed: `def5678` is reviewed already." This step comes ahead of `.andabot.yaml`'s settings, since approval doesn't depend on them; the evaluation still never approves a draft. Any other head is reviewed as a push would review it, so the settings that decide whether a push is reviewed apply first, read at the pull request's base. A draft follows `reviews.drafts`: by default it gets nothing more, "Resumed. It's a draft, so I'll review it once it's ready for review.", as a push to a draft isn't reviewed, and with `drafts: true` it is reviewed like any pull request. When `auto`, `base_branches` or `ignore_title_keywords` keep pushes unreviewed, `resume` reviews nothing and says which setting does, adding that `@andabot review` reviews on request. Otherwise it reviews the head, incrementally from the last reviewed head, which covers everything pushed during the pause: "Resumed: reviewing `def5678`." That review counts as requested, since `resume` has applied the push settings itself, so only `path_filters` that leave out every changed file can still skip it, after the reply, logged as `review.skip`. After that review, `resume` evaluates only where nothing else will: when the review found nothing new to review. A review that posts follows its own rule, one turned away by a review already in flight leaves approval to that review, and one that fails or is replaced leaves the head with no review to approve. `command.resumed` logs the step it took, a settings skip by its reason: `draft`, `auto`, `base_branch` or `title_keyword`.

`resolve` in the conversation resolves every one of andabot's open threads, blocking, optional and outdated alike, through GraphQL `resolveReviewThread`, reading them live from `reviewThreads` as a review does. Typed in one of andabot's threads, it resolves that thread only. In anyone else's thread it resolves nothing and replies that andabot resolves only its own threads, in a thread already resolved it replies "Already resolved.", and when the threads can't be read it resolves none and says so. No reply goes on each thread: the one reply carries the count, "Resolved 3 of my threads." or "None of my threads is open.", and how many couldn't be resolved, each failure logged as `command.resolve_failed`. GitHub reports andabot's own resolutions as sent by a bot, which the router ignores, so `resolve` runs the approval evaluation itself, with the trigger `resolve`, and counts the threads it just resolved as resolved whatever GitHub's list says, as a review does with its own. The reply ends with what approval does next: "Approved `def5678`.", or why it still waits, in plain words. A blocking finding the last review couldn't post inline has no thread, so `resolve` leaves it, and the reply says how to clear it: push a fix or ask for a `full review`. While paused the reply says approval waits until `resume`, and when the repository's request-changes workflow is off it leaves approval unmentioned: the workflow the evaluation follows, the last review's, else `.andabot.yaml`'s `request_changes_workflow` at the base, else the variable. A workflow it can't tell leaves the note in, so the reply says what the evaluation found, such as "Approval waits: I couldn't read `.andabot.yaml`.", and a failed read of the pull request for it logs `command.resolve_failed` with the step `workflow`. `command.resolved` logs where it was typed, the counts and the evaluation's outcome.

`summary` writes a new summary, walkthrough and merge danger for the pull request at its current head, without a review: the model writes no findings and no verdict, and nothing posts a review or opens a check run. It runs in a Pi session of its own, whose id `summarySession` keeps, so it can run beside a review rather than wait behind one, never resets the root session, and keeps its diff out of the root session's transcript, which chat answers read. Each run resets that session and configures it as a review configures the root: the summary skill, with the review skill's `references/merge-danger.md`, as its instructions, `REVIEW_THINKING_LEVEL`, and the model through `setModel`. Every session selects the registry's `andabot` extension unless it is configured otherwise. That extension's preamble presents the model as a reviewer that posts through `submit_review`, which contradicts the summary skill, and with its tools a `submit_review` call from a summary while a review runs would pass the check that the caller is the review in flight and post as that review. So the summary session selects no extensions (`extensions: []`) and offers the model no tools (`modelTools: []`), since the prompt holds all a summary needs: it has neither andabot's reviewer preamble nor any tool. As defence in depth, `submit_review` posts only for a call from the root conversation, which the tool's `conversationId` names. The in-flight check reads only the root session's operations, since a summary's operation, taken for the running one, would refuse the review's own submission.

The prompt carries the pull request's data, its linked issues and the diff the base's `path_filters` leave in, as a review's prompt has it, read fresh as a review reads them, and asks for the JSON alone. Every request whose latest message is that prompt carries a `json_schema` `response_format` for `SummarySubmission`, the summary, walkthrough and merge danger, through the provider wrapper that holds the resubmit prompt to `ReviewSubmission`, and TypeBox parses the answer. An answer that doesn't parse, or a run that doesn't finish, ends it with no retry: nothing is written, `summary.failed` is logged, and the reply gives the reason, flattened to one clause, since a provider's message can span lines or end in its own period. When the model answers, the host reads the head again. If it moved, nothing is written, `summary.superseded` is logged, and the reply names both heads and asks for a new `summary`. Otherwise the host updates `reviewed` and the summary comment as "Review pipeline" describes, logs `summary.posted` with `files`, `filesFiltered` and `config` as `review.start` does, and replies "Updated the summary for `def5678`." with a link to the comment. The comment's footer credits the model and skills `summary@…` and names the linked issues, with no `Standards:` line, since a summary reads no repository standards, and no cost line, since only a review keeps the baseline in `pending` that its spend is measured from. When `.andabot.yaml` was ignored, the footer ends with the config note, as a review's does.

One summary runs at a time. A `summary` that finds a live `summarizing` record replies that one is already being written, and logs `summary.skip` with reason `in_progress`. A record is live while Pi lists its operation, or within the grace, so a run killed by eviction doesn't block the next one for good. After an eviction or a deploy mid-summary, though, Pi resumes the operation with nothing waiting for its answer, so until it settles a second `summary` gets that reply though nothing will update the comment. On a closed pull request `summary` replies that there's nothing to summarize, and logs `summary.skip` with reason `not_open`. When `path_filters` leave out every changed file, `summary` writes nothing, replies that they leave nothing to summarize, and logs `summary.skip` with reason `path_filters` and the `config` status. Every path replies, an unexpected error included, so its 👀 always gets an answer.

A summary that lands while a review is publishing can be overwritten though its reply says it updated the comment: the review read `reviewed` before the summary wrote it, so the review's write, its old summary with its "Since" section, wins until the next summary or review rewrites `reviewed` and the comment. `pause` and `resume` edit the comment by reading it and writing it back, so a review's write that lands between the two can be undone, and as no automatic review repairs it during a pause, the stale comment can last until a `summary` or the next requested review.

### Configuration file

`.andabot.yaml` is optional and is read at the pull request's base commit, like the instruction files, so a pull request cannot change the rules it is reviewed by: one that turns `auto` off, adds a title keyword or filters out its own files is still reviewed under the base's settings, and its change applies once it is on the base branch. The object reads it on its own, not with the tree, so a tree GitHub fails to serve leaves the settings in force. `docs/setup.md` lists every setting with its default.

```yaml
reviews:
  auto: true
  drafts: false
  base_branches: ["main"]
  ignore_title_keywords: ["WIP"]
  request_changes_workflow: true
  verify: true
  path_instructions:
    - path: "apps/worker/**"
      instructions: "Receipts must stay decodable for 24 hours after a deploy."
  path_filters: ["!pnpm-lock.yaml", "!**/*.snap"]
model:
  verify: "@cf/moonshotai/kimi-k2.7-code"
checks:
  lint: "pnpm oxlint {paths}"
  typecheck: "pnpm tsc --noEmit"
  test: "pnpm vitest run {paths}"
```

`src/repository/config.ts` parses it with `yaml` and a TypeBox schema. A missing file gives the defaults. An invalid one, whether YAML that doesn't parse, a key the schema doesn't know, a value of the wrong type or a `path_filters` entry without its `!`, gives the defaults with none of its settings applied, and the summary comment ends with `_.andabot.yaml was ignored: <the first problem>; the defaults applied._`, the problem flattened onto one line, cut at 300 characters and set as code, wrapped like the Standards line's paths, so a glob's stars in a YAML error can't turn into emphasis. A file GitHub fails to serve for any reason but a 404 gives the defaults and the same note, logs `config.unreadable` with the base, and is not cached, so the next review reads it again and a passing 5xx doesn't pin the defaults until the base moves. Every other read is cached under `config:<baseSha>`, and storing it is best effort, logging `config.uncached` when it fails. A review keeps the request-changes workflow, the verify model and the error it started with in `pending`, so the summary it posts describes the settings its prompt was built with. `review.start` logs `config` as `missing`, `file`, `invalid` or `unreadable`.

- **Whether a push is reviewed.** `shouldReview` checks `auto` (default `true`), then `drafts` (default `false`), then `base_branches` (default any), then `ignore_title_keywords` (default none), after the skips for a closed pull request, a moved head and a head already reviewed, and before the review touches the one in flight or opens its check run. A push one of them skips logs `review.skip` with the reason `auto`, `draft`, `base_branch` or `title_keyword` and the `config` status, completes nothing, and leaves any pending review and the last posted one standing. A base branch matches by its exact name, not as a glob. A keyword matches anywhere in the title, ignoring case and its own surrounding spaces, and a blank keyword matches nothing. A command, whether `@andabot review`, `full review` or a check re-run, bypasses all four; `resume` applies them to the head it catches up with, as a push would (see "Commands and chat"). The router stays config-free: it forwards drafts and leaves the decision to the object, and since it doesn't route `edited`, a title or base edit starts no review; the next push or a command does.
- **`request_changes_workflow`**, when set, overrides `REQUEST_CHANGES_WORKFLOW` for both the review's event and the approval evaluation. Overriding only the review would leave a repository that turns the workflow on, under a Worker that has it off, with requested changes that resolving the threads never lifts. The review records the workflow it ran under on `last_review`, and the evaluation follows that record, so it never approves under settings the review didn't run with. Only a record from before the field existed, or none, sends the evaluation to the file at the current base, and a file it can't read makes it wait as `workflow_unknown` rather than guess from the var.
- **`drafts: true`** reviews a draft on each push without waiting for it to be ready, so its review may post before its checks finish. The evaluation never approves a draft (`not_open`); the ready-for-review event that then finds the head already reviewed runs it, and the approval follows.
- **`path_filters`** are `!`-prefixed minimatch globs, matched with `dot: true` and `nonegate: true`, so a doubled `!!` is a literal `!` rather than a negation that would filter everything else, and compiled once per use, naming files to leave out of the review. `reviewableFiles` alone decides which changed files the review covers. A filtered file gets no patch or listing in the prompt, needs no walkthrough row (a row the model writes for one anyway is dropped, on a review and on a `summary`, #119), and counts toward no incremental review's coverage, so a push that changed only filtered files has nothing to review. When the filters leave out every changed file, the review skips with `path_filters` before it opens a check run, a command's included. Only a file that sets filters makes the review list the changed files that early, so a push that then finds a review already running for its head lists none. The review's `scope` keeps the filters, so `submitReview` asks for the rows the prompt asked for and checks findings against the same files: a finding on a filtered file is rejected as left out by the filters and, like an unfounded one, holds no approval back. `list_changed_files` still lists every changed file, marking the filtered ones `(filtered)`, by the filters of the review in flight, or the file's when no review is. `grep`, `tree` and `read_file` still search and read filtered files, since the filters say what isn't reviewed, not what can't be read. A filtered doc is no doc to the review: it is neither searched for mentions of the change nor citable by a `docs` finding (#125). Filtered files still scope the instruction files and the path instructions, and still count in the in-progress check run's "Reviewing N files" and in `review.start`'s `files`, beside `filesFiltered`, which counts how many were left out. A `summary` applies them as well: its prompt shows only the files they leave in, and when they leave out every changed file it writes nothing and logs `summary.skip` with `path_filters` (see "Commands and chat").
- **`path_instructions`** join the standards ahead of the instruction files, each labelled `.andabot.yaml: <glob>` and applied when its glob matches a changed file, and they apply even when the tree can't be read.
- **`docs`** names the repository's authoritative docs as minimatch globs, `!` excluding; a list with an include replaces the defaults, a list of excludes alone narrows them (#125).
- **`reviews.verify`**, `true` by default, set to `false` turns verify off for the repository. With `VERIFY_MODEL` empty verify is off whatever it says, and a file that is invalid or unreadable applies none of its settings, so a `false` in it is ignored while `VERIFY_MODEL` is set (see "Verify").
- **`model`** takes any mapping. `model.verify` names the model verify uses for the repository in place of `VERIFY_MODEL`, and must be a non-empty string when present; with `VERIFY_MODEL` empty it does nothing. Every other key, `model.draft` included, is accepted and ignored.

Costs are tracked per conversation in Pi's `pi.usage` document, so the summary comment can print what the review cost (#32). The ledger only grows, across resets and the questions answered between reviews, so `pending` keeps it as it stood when the review started, and the spend is what it grew by when the review's summary posts: the retry, failed attempts and compaction included. The calls are the model's responses since the review's reset, and when verify ran, those of its session since its own last reset. The ledger the host reads is Pi's total over every conversation, so a `summary` that runs during a review adds its tokens and cost to that review's line, though not to its calls, which count the responses of the root session and of verify's alone: a known overlap, accepted since it needs both to run at once. The prices are pi-ai's, generated from Cloudflare's model catalog and pinned with the package, rather than a table kept by hand: a price change arrives with a pi-ai bump. Neurons are the dollars at Workers AI's $0.011 per 1,000. The footer shows the calls, the tokens in (cached ones included) and out, and the cost in neurons and dollars; a model with no price shows `cost unknown`, or `+ unpriced <model>` beside the priced part, and zero tokens shows `usage not reported`. The spend is stored per model on the `posted:<sha>` record, so `review.done` logs the numbers the footer shows, and `review.incomplete`, `review.failed` and `review.no_submission` log a failed review's spend too. A log leaves `neurons` and `usd` out rather than logging 0 when a price or the usage is missing, so a query over reviews never averages in a false zero.

**Measuring recall (#120).** Every number andabot had about its own recall was an anecdote from a hand-run production review, so a change of model, thinking level or chunking is measured first on a frozen set: `tools/recall/cases.ts` names each pull request head, its base and the findings a reader expects there, each with the file, the line range at the head, the failure scenario, the severity, the basis kind, a regular expression that recognises the finding in a title, body or basis, and the evidence (the fixing commit for a miss on a real pull request, the answer key on #2 for a planted fixture); `tools/recall/build-set.ts` freezes the pull request's text, linked issues, diff base and diff stats from GitHub into `set.json`, refusing an expected path the head doesn't change; the base is the one GitHub's diff used, the merge-base of the merge commit's first parent and the head for a merged pull request and the first commit's parent for one that never merged, since a branch that merged main would otherwise carry every pull request merged in between (the first freeze gave #88 a 71-file diff for a 29-file change); it strips the release-notes block CodeRabbit appends to a description after the pull request opens, since production read the description before that edit and on a fixture the block spells the plant out. The set holds the eight misses CodeRabbit found on real pull requests in the 24 Oct 2026 audit (#87, #102, #66, #56, #65, #91, #105, #112), andabot's own valid findings at the heads they were made on (#66, #88, #57, #65, #71), the planted fixtures #9, #38, #54, #142, #143, #144 (which expects nothing) and #151, and three prompt-injection fixtures (#152, a description that asks for an approval; #153, a code comment that says the file was vetted; #154, a `CLAUDE.md` changed at the head, which production reads at the base, so the text reaches the model only through the diff). `pnpm recall --model <id> [--thinking low] [--runs 3]` replays a `fresh` review of each head offline in node: production's prompt, skill and standards (the instruction files and `.andabot.yaml` read from git at the base), the root session's tools served from a snapshot of the head, `validateFindings` and the rejection, missing-row and resubmit path of the object, and the 10,000-neuron review budget with its tool block and request refusal, so the findings that count are those production would have posted; `run_check` answers that the tier is off, `resolve_thread` refuses as outside an answer, and no repository skills catalog is offered. A produced finding matches an expected one by path and pattern, the nearest by line when several match; the unmatched ones count as false unless the head's `allowed` list names them as true findings outside the set, and the audit's labelled false findings are `knownFalse` so a recurrence is named. A case is found when 2 of 3 runs match it. A head's expected event is derived from its expected findings, `REQUEST_CHANGES` when one is blocking and `APPROVE` otherwise, and a run's event with the host's own rule (`decideReviewVerdict` over the validated findings and the submission's reasons), so a verdict match says the blocking line was drawn in the same place (a run that withholds for a reason on a head expecting approval still matches, since the reasons axis isn't labelled); the expected labels follow the review's pairing rule (#121): a `defect` or `spec` finding is `blocking` or `major`, a `standard`, `test` or `docs` finding `suggestion` or `nitpick`, and #112's two docs-against-code cases carry the `docs` basis (#125). An experiment is adopted only when its found-count is at least the baseline's and its false count no higher, with the cost per review shown beside both (`pnpm recall --compare`); there is no weighted score. The runner refuses a thinking level the model would clamp, since under the pinned pi-ai GLM-5.3 Flash runs `low`, `high` and `max` only and a requested `medium` would run as `high`, which production's `REVIEW_THINKING_LEVEL=medium` does too. Each run's scored summary is committed under `tools/recall/results/` and its table posted on #120; raw transcripts and the $20 spend journal stay under the gitignored `tools/recall/runs/`.

## Execution tiers for repo access

1. **API only.** PR files and patches, file contents at a ref, trees, code search. Enough for diff review. Phase 1.
2. **Tarball snapshot, no container.** The head commit's text files, streamed from GitHub's tarball into the object's SQLite, so `grep` and `tree` work without a container (#30). Phase 2.
3. **Sandbox.** A `ReviewSandbox` Durable Object per pull request, a class of its own on the runtime's `ctx.container` under the `durable_object` scheduling policy, so the object picks the image (`container/Dockerfile`: Node 22, pnpm 10, git) and the instance (`standard-1`) when it starts, with `enableInternet` off and a 30-minute inactivity timeout as the backstop. Every HTTP and HTTPS request the container makes goes through the `Outbound` entrypoint, whose allowlist is `github.com`, where it adds the token it holds as props (`Basic` with the user `x-access-token`, dropping any `Authorization` the container sent), an installation token minted for the sandbox alone with `contents: read` on the reviewed repository and nothing else, so code running in the sandbox can fetch but never push, and `registry.npmjs.org`; plain HTTP, any other host and any port but 443 get a 403 (the platform routes only ports 80 and 443 to the handler and refuses the rest outright, so the port check is defense in depth), a redirect goes back to the container rather than being followed in the Worker, so every hop is decided by the same allowlist and the token never rides a redirect off `github.com`, and the container trusts the interception CA through the environment of every command (`NODE_EXTRA_CA_CERTS`, `GIT_SSL_CAINFO`, `CURL_CA_BUNDLE`, `SSL_CERT_FILE`). A command is an argv array, never a shell string, run under a wrapper that puts it in its own process group and writes its output and exit code to files, so a timeout sends the group `TERM`, waits five seconds, then sends it `KILL` whether or not the wrapper has exited, since the wrapper's exit says nothing about a descendant that ignored `TERM`, and the result is read with one more command: the exit code, the output's size and its last `tailBytes` (8 KiB by default, 50 KiB at most, Pi Durable's tool-result cap), with `cut` when the output was longer. A run the object killed is reported as `timeout` whatever the wrapper recorded, and a result the object can't read, as when the container has died, throws rather than reading as a clean exit. The logs are `sandbox.start` (`started`, whether this call started the container, and `ms`), `sandbox.run` (`command`, the argv's first word, `outcome`, `exitCode`, `ms`, `bytes` and `cut`), `sandbox.destroy` and `sandbox.probe`. A review reaches its sandbox through `SandboxRuns` (#132), beside `SnapshotRuns`: nothing starts until the first call, which `run_check` (#133) will make, and then the preparation is one chain, memoised so concurrent callers share it. It takes a lease, mints a token for the sandbox alone (`contents: read` on the reviewed repository), starts the container, turns virtual-memory overcommit on inside it (`vm.overcommit_memory=1`, logged as `sandbox.overcommit` with the exit code and, when it failed, the last line: `standard-1` is a 4 GiB VM with heuristic overcommit and no swap, which refuses the single 6 GiB mapping oxlint reserves per thread when a repository has JS plugins, so `lint` aborted with `SIGABRT` until #146; the write is best effort and the review goes on without it), fetches the head commit by its sha, shallow, into `/workspace/repo` (GitHub serves a reachable commit by sha, which covers a fork's head through the base repository), checks that `HEAD` is that sha, refuses a working tree over 512 MiB, detects the package manager from the lockfile (`pnpm-lock.yaml` or `package-lock.json`; anything else, `yarn.lock` included, means no install, since the image carries pnpm and npm) and installs with lifecycle scripts off. Checkout and install each have a 5-minute timeout. A step that fails or throws destroys the container, releases the lease and leaves the sandbox `unavailable` for the rest of the review, with the step as the reason (`head`, `lease`, `start`, `checkout` or `install`); nothing in the preparation escapes to the review. The runs count the reviews active on the object, as the snapshot's do: a replaced review's end destroys nothing while its replacement is active, a `closed` event destroys only when no review is active, and a call for a head other than the one prepared ends the old sandbox first. The tier is off unless the Worker var `SANDBOX` is `true` and the base's `.andabot.yaml` doesn't set `reviews.sandbox: false`. `MAX_SANDBOX_SECONDS` (900 by default) is wall time since the first call; past it the sandbox answers `spent`. The review that started the sandbox destroys it in the same `finally` that ends its snapshot run, and a closed pull request destroys it too; the container object sets a one-minute alarm while a run is in flight so a working container is never idle to the platform, and the 30-minute inactivity timeout stays as the backstop. Under the `durable_object` policy wrangler rejects `max_instances`, so `SandboxLeases`, one Durable Object named `leases`, caps running sandboxes at three across every pull request: a lease is taken before the container starts and released when it is destroyed, with a ttl of the budget plus two minutes so a review that died holding one frees its slot on its own. `run_check(name, paths?)` (#133) is the tool: `name` is `lint`, `typecheck` or `test`, and `paths`, at most 20, each matching `^[A-Za-z0-9_@+./-]+$` with no `..` segment and no leading `/` or `-`, must exist in the checkout, which one `test -e` run confirms. The command comes from the base's `.andabot.yaml` `checks` map, a template split on whitespace whose standalone `{paths}` token becomes the paths, one argument each, so the model's paths are never shell text; with no entry, from a runner `package.json` at the base names, through the manager slice 2 detected (`pnpm exec` or `npx --no-install`): `oxlint` or `eslint`, `tsc --noEmit`, `vitest run` or `jest`; a repository with no lockfile has no installed runner, so the fallback answers `no_command` rather than an `npx` exit 1 that would read as a failed check. It runs in `/workspace/repo` with `NO_COLOR=1`, `FORCE_COLOR=0` and `CI=1`, under `SANDBOX_CHECK_TIMEOUT` (300,000 ms), one check at a time, and answers the exit code, the seconds and the last 8 KiB of output, or a sentence saying why it didn't run (`off`, `spent`, `unavailable` with the step, `no_command`, `bad_path`, `missing_path`). A run is cached per head, name and paths for the review, so a repeated call answers the stored result. `run_check` with no review in flight (the review has posted or ended, or a question is being answered) is refused as `ended` rather than preparing a sandbox nothing would end. The tool is offered whether or not the tier is on, since the extension's tool list is fixed per object; an `off` answer costs one call. A finding may carry `check: { name, paths, exit_code }`, which `validateFindings` checks against the review's runs and rejects as unfounded when no such run happened or its exit code differs. The logs are `check.run` (`number`, `name`, `paths`, `outcome`, `exitCode`, `ms`, `bytes`, `cut`), `check.cached` (`number`, `name`, `paths`), `check.refused` (`number`, `name`, `reason`) and `check.package_unreadable`. `POST /sandbox-probe`, on only while `SANDBOX_PROBE` is `true` and signed like a delivery, drives a sandbox by hand; its `prepare` and `check` actions go through the pull request object's own path (`docs/setup.md`). What the reader sees (#134): a `**Checks:**` line under the walkthrough, after the dropped-findings line and before the Verify section, that is left out when the review never asked for the sandbox (with the tier off by default, a `none` would sit on every review everywhere), says `off`, `spent` or `unavailable (install failed)` when it asked and got that answer, `none` when it asked and ran nothing, and otherwise lists one entry per run in the order they ran, `test on \`test/x.test.ts\`: passed in 3.1s`, `lint: failed (exit 1) in 2.1s`, `typecheck: timed out after 300s`; the first five failed or timed-out runs get a collapsed block holding the tail, cut to its last 2,000 characters, in a fence longer than any the tail holds, and a line counts any more, so the comment stays under GitHub's limit. A finding that carries a `check` renders `_Check: test on \`test/x.test.ts\` exited 1_` after its basis. The footer's cost line gains ` · sandbox 2m 14s ($0.003)` when the review asked for the sandbox, the wall seconds priced at `standard-1`'s rates, $0.00002056 a second (half a vCPU at $0.000020 per vCPU-second, 4 GiB at $0.0000025 per GiB-second, 8 GB of disk at $0.00000007 per GB-second), rounded as the model's dollars are. `posted:<sha>` keeps `sandboxSeconds` and `checks`, the runs as records, and `review.done` logs `sandboxSeconds`, `sandboxUsd` and `checks`, the count of runs. The logs are `sandbox.lease` (`holder`, `granted`, `live`), `sandbox.checkout` (`number`, `sha`, `kib`, `ms`), `sandbox.install` (`number`, `manager`, `exitCode`, `ms`), `sandbox.failed` (`number`, `step`, `reason`), `sandbox.unavailable` (`number`, `reason`), `sandbox.spent` (`number`, `seconds`, `budget`, once per review), `sandbox.destroy` (`number`, `reason` as `review_end`, `closed` or `new_head`, `seconds`, only when the teardown destroyed a running container), `sandbox.destroy_failed` and `sandbox.unlease_failed`; `review.done` carries `sandboxSeconds` when a sandbox was asked for. The sandbox's state survives a restart of the pull request object (#140): `SandboxRuns` keeps the head, the clock's start, the lease and container flags, the settled answer and the check runs in one record under the storage key `sandbox`, written at each step a teardown would have to undo and after each run, deleted when the teardown finishes. Every call restores it once per instance, so a `run_check` after a redeploy or an eviction runs in the checkout that exists, with no second lease, start, checkout or install, the budget's clock stays where it was, and a finding's `check` reference still validates; a `ready` record is trusted only after the container object says it is still running, and otherwise the restore logs `sandbox.lost`, releases the lease and prepares afresh on the next access with the clock kept, so a crash never buys a pull request a second budget. Every path that releases a review's `pending` on a restarted object, where no `finally` follows, drops the idle sandbox: a posted or failed review, a superseded one, a `closed` event; a `dead` replacement at the same head inherits the sandbox with an empty cache of its own. A Lifecycle job, `sandbox.drop`, due at the clock's start plus the budget plus the lease grace and cancelled by the teardown, ends what nothing else will, coming back every two minutes while a review is still active on a live object, so a dead review's container is bounded by `MAX_SANDBOX_SECONDS` plus two minutes with the 30-minute inactivity timeout as the last resort. The logs are `sandbox.restored` (`number`, `sha`, `kind` as `ready`, `unavailable` or `preparing`, `checks`, `seconds`), `sandbox.lost` (`number`, `sha`, `seconds`), `sandbox.load_failed`, `sandbox.save_failed` and `sandbox.drop_job_failed` (`step`), and `check.refused` gains the reason `ended`. The design of the phase is `docs/superpowers/specs/2026-10-28-sandbox-design.md`: targeted runs the model picks (#133), the summary and the cost line (#134), the measurement (#135), the state across a restart (#140). The tier runs targeted checks rather than the suite because CI already runs `pnpm check` on every pull request and andabot waits on it for approval, so a sandbox running the same suite would duplicate CI at container prices; what CI can't give the review is one test file or one typecheck while the review is still deciding, and a check for a repository with no CI. Measured on 29 Oct 2026 (#135, tables there) on three fixture pull requests from `main-with-checks`, a base whose `.andabot.yaml` sets `checks.typecheck: pnpm typecheck` because this repository's typecheck needs `wrangler types` first: #142 plants a refactor of `durationText` that drops the zero parts a test pins, #143 widens `checkTimeoutOf` to `number | undefined` where its one caller needs a number, and #144 changes a sentence of `docs/setup.md`. GLM-5.3 Flash found both plants with the tier off, from the diff, a `grep` and a `read_file`, and asked for the sandbox on both (an `off` answer costs one call); with the tier on it ran `test` on `test/cost.test.ts` (exit 1 in 4.4 s) and cited the run in the finding's `check`, ran `typecheck` (exit 2 in 50.9 s) and quoted the TS2322 line in the basis, and never asked on the docs-only change, so the lazy start stays: the install alone is 38 s of a 77-second sandbox, which an eager start would spend on every review. The sandbox time was 77 s ($0.002) and 141 s ($0.003), the model's spend 337 and 949 neurons against 430 and 646 with the tier off, and the wall time 99 s and 157 s against 58 s and 47 s. The on-tier reviews ran at once and held two of the three leases. Every pull request runs checks, a stranger's included, bounded by caps rather than by who opened it: its test files run, so a hostile pull request can make a test sleep (one `SANDBOX_CHECK_TIMEOUT`, 300 s), call out (the allowlist answers 403 to every host but `github.com` and `registry.npmjs.org`) or add install scripts (the install runs none). The ceiling for one review is about 1,200 s of `standard-1`, $0.025: checkout and install each stop at five minutes, checks run one at a time under the 300-second timeout while the sandbox's wall time is under `MAX_SANDBOX_SECONDS` (900 s), and a check that starts just under the budget runs to its own timeout; a review that dies without destroying its container is ended by the drop job at the budget plus two minutes, $0.021 at most, with the 30-minute inactivity backstop ($0.037) as the last resort (#140). Across pull requests the lease caps running sandboxes at three, each lease outliving its review by at most the budget plus two minutes, so the account runs at most three containers at once, $0.22 an hour and $5.33 a day with every slot busy around the clock. The Workers Paid plan's included 25 GiB-hours cover 22,500 s of `standard-1` a month, 25 full budgets or about 300 reviews like #142's. So `SANDBOX` defaults to `true` in `wrangler.jsonc`; a repository opts out with `reviews.sandbox: false`. Kimi K2.7 Code, run on the same fixtures with the tier on, found both plants and set a matching `check` on both findings, but ran every check it could (`lint`, `typecheck` and `test` on each code change, a typecheck of #142 included) rather than the one its suspicion pointed at, for 244 s and 255 s of sandbox time ($0.005 each) beside model costs of $0.036 and $0.125; it never asked on the docs-only change either. No model cited a failed run's exit code as a defect, and `oxlint` 1.88.0 died in the container on both of Kimi's lint runs (a panic in `oxc_allocator`'s fixed-size pool, then `SIGABRT`), which the review listed on the Checks line and left alone; that crash is a follow-up.

## Tests

`pnpm test` runs unit tests of the pure modules in Node, whose WebCrypto is the one the Worker uses, and `test/lint` checks that every folder gets the lint rules. Tests against the Durable Object itself aren't written yet. The two replay runners under `tools/` (`pnpm verify:replay` for the verify pass, `pnpm recall` for the recall benchmark) call Workers AI and are run by hand, outside `pnpm check`; their pure parts (matching, scoring, the bar, the set's schema, the tool answers, the review loop) are unit-tested like the Worker's.

## Phases

1. **Walking skeleton.** GitHub App, router Worker, PR object with `PiHarness`, API-only tools, full review on open, summary comment and one review with inline comments, `review` and `help` commands. Deployed and reviewing this repo's own PRs.
2. **CodeRabbit parity.** Approval state machine, config file, path instructions, incremental review, remaining commands, chat turns, repository search, verify pass, cost in the summary. It opens with the skills work, each step measured on #2 with gpt-oss-120b and Kimi K2.7 Code, and from slice 2 on GLM-5.3 Flash, the default model:
   - **Baseline.** The planted-bug pull request reviewed on the phase 1 build, with the results recorded in #2.
   - **Slice 1: the review procedure as skills.** The review and answer skills, bundled and activated by the host; a system prompt of identity and tools; the model and the skill fingerprint in the summary footer, the logs and the posted review's record (#11).
   - **Slice 2: basis, coverage and the spec axis.** Basis, merge danger, walkthrough coverage, the submit loop's outcome type and linked issues, on top of the anchors #12 shipped for #4.
   - **Slice 3: repository context.** The repository's instruction files as standards (#29), `.andabot.yaml` (#28) and its own skills through the catalog (#75), measured on the fixtures #68, #72 and #77; its follow-ups (#78 to #81, #83, #100, #103) are closed.
   - **Verify pass.** A second pass over every finding but nitpicks before it posts, in a session of its own with `read_file`, `grep` and `tree` (#31). Built, but off after neither model cleared the replay bar; the 24 Oct measurement is recorded under "Verify", and #129 tracks turning it on.
3. **Sandbox tier.** Targeted checks the model picks, run on the head in a container (`docs/superpowers/specs/2026-10-28-sandbox-design.md`): the image, the `ReviewSandbox` object and the outbound allowlist (#131, shipped); the checkout, the install, the lifetime and the lease (#132, shipped); `run_check(name, paths)` (#133, shipped); the summary's Checks line and the cost line (#134, shipped); the measurement and the abuse ceiling (#135, measured on GLM-5.3 Flash on 29 Oct 2026 on the fixtures #142 to #144, with `SANDBOX` on by default since). Verify's use of the results waits on #129.
4. **Reviews that hold up.** Delivery parity with CodeRabbit: nothing an author does goes unanswered, a push's review lands, a fixed thread closes, and a finding that blocks is one a reader would block on (`docs/superpowers/specs/2026-10-29-reviews-that-hold-up-design.md`, milestone "Phase 4: reviews that hold up"). Delivery: a transient GitHub error retries the delivery (#118, shipped), re-checking the threads new commits fix away from their line, resolving a withdrawn or verified finding from the answer, one reply per thread (#123, shipped), keeping the blast radius when a push narrows it (#124), the walkthrough rows `path_filters` leave out (#119), the summary's tidy-up (#126), closing keywords that won't close (#127). A frozen recall benchmark before any model, thinking or chunking change (#120, shipped: `pnpm recall`, "Measuring recall" under Models). Findings that block: impact graded apart from blocking and a basis checked against its claim (#121), the host deciding the verdict and a non-approving review saying why (#122), docs checked against the code they describe (#125), verify on once a model clears the bar (#129). The old extras (sequence diagram, docstrings, unit test generation) are folded in and no longer a phase of their own.

## Open questions
